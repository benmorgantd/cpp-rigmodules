# Decisions: Assets, looks and the build's scene output

The asset and its namespace, skeletons, rigs and looks, attachments, naming, the layers, selection sets and groups the build makes, and the art stages. Part of the decision log: the Index and the open items are in [`../decisions.md`](../decisions.md). Entries are in number order.

### D29. The asset owns its namespace, its rig variants and its files
**Status:** Decided (2026-11-08). The scene side is built and run in mayapy 2026. The file model, versions, registry and handlers are built on mayadev branch `asset-model` (not merged), as described in `asset-model.md`. **Amended by D54 (built 2026-11-16):** the scene side below is replaced. A namespace holds one rig, its default is `{asset name}_{rigName}`, and the rig root stores `assetId` itself: `assetRootModule` is removed.

An asset is the top-level container for a character, prop, vehicle, vfx element or environment piece. In a scene, one `assetRootModule` per flat namespace owns every rig variant built into that namespace. On disk, the asset is a folder under `RIGGING_PROJECT_DIR` holding an `asset.json`, and its backslash-separated id is that folder's relative path. Full design: `asset-model.md`.

- **Author's answers (2026-11-08):**
  - Keep `|` in asset ids, because existing tools depend on it (rejected: `/`). **Amended 2026-11-12: the separator is now `\`**, see the end of this entry. Depth varies (rejected: always `project|type|name`, which is idealistic once assets end up everywhere). Ids compare case-insensitively.
  - The asset comes from `createRigFromTemplate(asset=...)`, so templates can be shared between assets (rejected: an `assetId` template key, which ties a template to one asset and goes stale when a template is copied).
  - Namespaces are flat, one per asset instance (rejected: nested `asset:variant`). The default is the id's last token, and `namespace` overrides it (`hero_damaged`). Variants share the namespace, and the variant is the rig root's `rigName`.
  - `rigType` is removed, and asset types come from the project's `project.json` and are stored in `asset.json`. The C++ keeps no asset type list (rejected: the `Mesh`/`Rig`/`Other` enum, which described file kinds and repeated what the project defines).
  - Variants share one skeleton. A variant may add joints, never remove them. Meshes, weights, textures and shaders are per variant.
  - Each rig root stamps what built it (`rigVersion`, `pluginVersion`, `publishVersion`). Tools check the stamps against the latest publishes to flag out-of-date imports.
  - Mainline only: one stream, no release-stream tooling, because one person maintains it.
  - Under Perforce, nothing shared is written on a routine save. Depot files change only when someone deliberately changes that asset: `asset.json` holds only type and skeleton, variants are folders, publishes are new folders with `<UTC time>Z_<user>` ids, the registry is an in-memory scan, and local versions live outside the workspace. Saves go through a source-control adapter that does nothing by default. Rejected: a shared `registry.json` written on every save (constant checkouts, merge conflicts on every integrate), sequential publish numbers (collide), changelist numbers as publish ids (renumbered on submit), and a per-machine registry cache file (still needs the walk, adds staleness).
  - The file model is Python in mayadev, on a new branch, because it departs from mayadev's current asset package. D24 stands: RigModules C++ never resolves a path from an asset id.
  - Where a file lives is kept apart from how it is saved and loaded. Save and load are per-file-type handler stubs.
  - Local version copies are wanted alongside source control. Artists go days between submits, and personal work has no Perforce.
  - Asset data must be readable without opening Maya: per-asset `asset.json`, a `project.json` holding the asset types and file types, and a registry cache. The registry tracks shared skeletons, so assets that can share poses and animations, and the dependents of a changed skeleton, come from one query.
  - The environment variable is `RIGGING_PROJECT_DIR`.
- **Built (2026-11-08):**
  - `createRigFromTemplate` needs `asset`, checks it (backslash-separated tokens of letters, digits and `_`), and defaults `namespace` to its last token.
  - The build reuses the namespace's asset root or creates one. The read phase fails when the namespace holds more than one asset root, when the asset root's `assetId` differs from `asset` (case is ignored), or when a rig root under it already has the template's `rigName`.
  - Before this change, the asset root's id came from `rigTemplateName` by mistake, and every build made a new asset root.
  - Rig roots get `pluginVersion` (set by the build from `PluginInfo::Version`, which `MFnPlugin` also registers) and `publishVersion` (a string holding the publish id, empty until the publish step sets it).
  - Removed: the template keys `assetId`, `assetType` and `rigType`; the `assetType`, `assetData` and `rigType` attributes; and `AssetType` and `RigType` in `maya/shared/`.
- **Consequence:**
  - Every template with `assetId`, `assetType` or `rigType` now fails as having unknown keys. No legacy templates need to survive.
  - Every `createRigFromTemplate` call needs `asset`, and the default namespace moves from `rig` to the asset's name.
  - Two templates with the same `rigName` can't be built into one namespace.
  - Pose and animation data aren't affected: no control, attribute or socket names changed.
- **Amendment (2026-11-11, author):** the `rig` file type ends with `_rig`, `variants/{variant}/{name}_{variant}_rig.ma`, like `_skeleton` and `_model`, so every Maya scene's role reads from its name. It is the default in mayadev's `Project.create`. An existing `project.json` keeps the layout it was written with until edited, and a rig saved under the old name needs renaming by hand.
- **Amendment (2026-11-12, author):** the asset id separator is `\`, not `|` (`shooter\main\characters\hero`). Done in RigModules and mayadev together (`core/AssetId`, `bmaya.asset.assetid`, their tests and docs). A `|` id is now invalid everywhere, with no migration: no rigs or files need to survive.
  - **Costs accepted:** `\` is the escape character in Python and C++ string literals, JSON, MEL and regexes. A Python id is written `"shooter\\hero"` (or a raw string), a JSON file holds `\\`, a MEL call needs `\\\\`, and a regex needs `re.escape`. Validation rejects control characters, so a stray `\n` or `\t` in a non-raw literal fails loudly instead of building a wrong id. `maya.cmds` passes the flag value through unchanged.
  - **Why it was acceptable:** `|` is also Maya's DAG path separator, so an id and a node path could be confused. Ids only split and join through `AssetId` and `bmaya.asset.assetid`. The id maps to a Windows folder path, so the separator matches the disk. Tokens stay letters, digits and `_`, so `\` can never appear inside one.
  - **Rejected:** `/` again (the pass the earlier amendment planned is replaced by this).

### D30. mayadev stays the pipeline repo, and rigs build anywhere before an asset exists
**Status:** Decided (2026-11-08). Steps 1 to 5 are built, except the template authoring UI: RigModules side run in the mayapy suite, mayadev side in its mayapy tests. Branch `asset-tools` is merged into mayadev main (checked 2026-11-09).

The author considered starting a new pipeline repo, because most of mayadev changes with the new asset and rigging systems. Decided: keep mayadev, tag its legacy state, delete the legacy code, and build the new tools there. A rig can be built and iterated on anywhere, before its asset folder exists. Tools that know about assets use the asset's paths when the rig's asset folder exists, and fall back to a file dialog when it doesn't.

- **Why keep the repo:** the parts that survive (`core/`, the events registry, `qtbase`, the tool registry and menus, the startup, skinning) keep their history and blame, and `mayadev.mod`, `MAYADEV_ROOT`, `userSetup.py` and the RigModules menu keep working unchanged. Deleting the legacy code gives the same clean slate a new repo would, and the tag keeps it readable as reference.
- **Rejected:** a new repo. It would lose that history and rewire the whole startup. It stays an option if a public portfolio repo without the legacy history is wanted, started from the cleaned-up tree. A rename of mayadev is also left for later.
- **Why build anywhere (author, 2026-11-08):** riggers iterate on a template and skeleton long before an asset is worth creating. The build already needs only an asset id (D29), never a folder.
- **Order:**
  1. In mayadev, commit or stash the uncommitted legacy work, then tag main `legacy-rig-builder`.
  2. Merge branch `asset-model`.
  3. On a cleanup branch, delete the legacy builder, legacy modules, `rigManager`, the legacy `bmaya.maya.asset`, and the legacy constants that read `RIG_TEMPLATES_DIR`, and fix startup and menus so nothing imports them.
  4. Build the RigModules `python/` query from any rig node to its asset id, variant (`rigName`), namespace and stamps (D24, D29).
  5. Build the new mayadev tools on it: New Asset and New Variant (replacing the legacy AssetCreator), asset-aware shape save and load, Save Rig, Build Rig from Asset, then the template authoring UI that replaces `rigManager`.
- **New Variant writes the variant's `template.json`.** A variant is a folder holding its template (D29), so creating one is a real write, not an empty folder, and the rule that folders appear only on write holds. `Asset.create` still writes only `asset.json`.
- **Built (2026-11-08):**
  - mayadev: main tagged `legacy-rig-builder`, `asset-model` merged. On branch `asset-tools`, the legacy code is deleted (builder, modules, shapes, templates, `rigTools`, `activerig`, `rigManager`, legacy `bmaya.maya.asset`, the `RIG_TEMPLATES_DIR` constants, their menu tools and docs). A copy of it sits in mayadev's untracked, ignored `legacy_reference/` for reading.
  - RigModules: `getRigInfo` (any rig root, module or control to its rig root, asset root, asset id, variant, namespace and stamps, as JSON), on new `RigTraversal::getOwningRigRoot` and `getAssetRoot`. `getMirrorControl` now uses `getOwningRigRoot`.
  - RigModules `python/rigmodules`: `query.get_rig_info`, `query.get_rigs(namespace)`, the `RigInfo` dataclass, and `template.get_rig_name`. `RigModules.mod` puts `python/` on `PYTHONPATH`. It adds no plugin path yet, because a loaded `.mll` locks the build output.
  - mayadev `bmaya.maya.assettools`: New Project, New Asset, New Variant, Save Skeleton, Build Rig from Asset, Save Rig, and asset-aware Save and Load Control Shapes, in the RigModules menu. A `template` handler copies a template into the variant and checks its `rigName` is the variant.
- **Author-facing choices made while building (2026-11-08), open to change:**
  - Once a rig's asset folder exists, the shape and rig tools always use the asset's paths, and loading a shape file the asset doesn't have is an error, not a dialog. A file never lands in two places.
  - Save Rig needs the variant's template in the asset first (New Variant). Without it the rig file would sit in a folder that isn't a variant.
  - Build Rig from Asset refuses a namespace that already holds a rig. Variants share one skeleton, so a second variant should reuse the joints already there rather than import them again, and that isn't built.
  - The rig tools act on the active rig (author, 2026-11-08), so nothing has to be selected. mayadev's `bmaya.maya.activerig.ActiveRigTracker` follows it, modelled on the legacy tracker: selecting any control, rig-driven joint, module or rig root makes its rig active, and it stays active while other things are selected. File new and open take the scene's first rig. Startup starts the tracker when the plugin loads. Without a tracker, the selection's rig, then the scene's first rig. The asset id dialogs always open, filled in with the active rig's asset id.
  - `getRigInfo` accepts joints, through the module that drives the joint's `offsetParentMatrix`, and returns `""` with no error for any node outside a rig, so a selection callback stays quiet. Rejected: a Python pre-check by node type in mayadev, which would copy RigModules node names (D24).
- **Not built:** the template authoring UI (it needs a module interface query command first, D24). Building a second variant into a namespace. (Importing the variant's model and loading its weights in Build Rig was built 2026-11-09, D35.)
- **Consequence:** `getRigInfo`'s keys, `RigInfoKey::Namespace`, and the `rigmodules.query` and `rigmodules.template` names are public API for mayadev. The template authoring UI validates through RigModules `python/`, never with its own copy of the template rules (D24).

### D38. The build makes three display layers, found by message attributes on the rig root
**Status:** Decided (author, 2026-11-11). Built and tested in Maya 2026 (`DisplayLayers` in `test_create_rig.py`).
After the modules are built, `createRig` replaces `jointsLayer`, `meshesLayer` and `controlsLayer` in the rig namespace (`RigNaming`) with new layers holding the input joints and every control, and an empty mesh layer whose display type is Reference, so the model isn't selectable while animating (`DisplayLayerScene::replaceLayers`, `DisplayLayerSpec::displayType`; the C++ enum mirrors Maya's `displayType` values and a test checks them, author, 2026-11-18). Each layer's `message` connects to one of the static `jointDisplayLayer`, `meshDisplayLayer` and `controlDisplayLayer` message attributes on the rig root (`RigAttr`). There is no array of all layers: a tool wants a layer by role, and the three attributes give that (author, 2026-11-11).
- **Why:** animators and tools toggle or lock a rig's parts as a group, and the layers are the lookup a tool uses, not their names. The array and the three attributes both exist because the author asked for both: the array lists the layers, the attributes name the role. Layers are plain `displayLayer` nodes made in the same `MDagModifier` as the rig, so undo and redo cover them. Rejected: MEL `createDisplayLayer`, whose undo would run apart from the modifier's.
- **Deletion is by name,** only the three layers, so an animator's own layers in the namespace survive. A second rig variant built into the namespace replaces the first variant's layers, because the names are per namespace.
- **Meshes come from the model import, not the build** (author, 2026-11-11). The model file is imported after the build (mayadev `build_rig`), so the build can't see it, and scanning the namespace would also catch meshes that aren't the model. The mesh layer starts empty, and the importing tool calls `rigmodules.displaylayers.add_meshes(rig_root, new_nodes)` with the import's new nodes. Python, not a command: it only reads the `meshDisplayLayer` attribute and calls `editDisplayLayerMembers`, which is undoable. Rejected: a C++ namespace scan at build time.
- **Members:** a node already in another layer is moved to the rig's layer. An empty layer is still made, so the lookup always works.
- **Controls layer hides on playback** (author, 2026-11-14): `controlsLayer.hideOnPlayback` is on, so controls aren't drawn while the timeline plays. This is the cheapest answer to the control draw cost in D37, since the custom draw override never runs. An animator can turn it off per layer in the Layer Editor.
- **Consequence:** the layers are public API (names and attributes). The layer manager is used the way `createDisplayLayer` does: `identification` and `displayOrder` are the first free id, and the layer connects to `layerManager.displayLayerId[id]`.

### D39. The build makes selection set hierarchies for controls and skin joints, found by markup
**Status:** Decided (author, 2026-11-11, restructured the same day). Built and tested in Maya 2026 (`commands/test_selection_sets.py`).
After the display layers, `createRig` replaces the rig namespace's selection sets (`objectSet`, `SelectionSetScene::replaceSets`) with two hierarchies, `controls_set` and `joints_set` (the skin joints only). Each holds `<kind>_left_set`, `<kind>_right_set`, `<kind>_center_set` and `<kind>_modules_set`, and the modules set holds one `<module>_<kind>_set` per module that owns members. `SelectionSets::planSets` in `core/` lays out each kind from `{module, side}` items, so the layout is Maya-free. Sets carry a JSON `setMarkup` (`markupVersion`, `kind`, `role`, `side`, `module`) and connect to `rigRoot.selectionSets`.
- **Why:** animators and skinners select a rig's parts as groups, and skinning tools need "the skin joints of this module or side" as data. Sets keep that in the scene, where an animator can also use them in the Outliner.
- **First version rejected (author):** it made 28 sets on the five-module test rig, with an "all" set per kind (controls, every joint, skin joints) holding members both directly and through module subsets, so a node could be in a set twice. Now there is one top set per kind that holds only other sets, and the items sit in exactly one side set and one module set. Selecting the top set selects each item once. The all-joints set is gone: the joints hierarchy is the skin joints, which is what skinning and animator selection need.
- **Markup, not a message attribute per set:** one array plus per-set markup follows D25 (D38 has three attributes), and `rigmodules.selection.find_set` filters it. `role` tells the top set, the modules container and a module set apart, since none of them has a side.
- **Module and joint ownership:** a control's module is its `controlMessage` owner, and a joint's module is the one driving its `offsetParentMatrix` (`RigTraversal::getJointModule`, now public). A skin joint no module drives is in its side set only. A module subset exists only when it has members, so Layout has controls but no joints set. The side sets always exist, even empty, so a lookup never has to handle a missing set.
- **Skinning helpers are Python** (`rigmodules.selection`): `get_skin_joints`, `select_skin_joints`, `get_missing_influences` and `get_extra_influences`. No new command: they read sets and markup only.
- **Build detail:** the `setMarkup` attribute is added by an internal `doIt`, because its value can only be queued once the plug exists. Sets are made in the same `MDagModifier` as the rig, so undo and redo cover them. Deletion is by name and covers only these sets, like D38, so a rebuild into a namespace whose modules changed leaves the old module sets behind.
- **Consequence:** set names, the `selectionSets` and `setMarkup` attributes and the `kind` and `role` values are public API.

### D43. The build makes `rig_all` over the rig and `mesh_grp` for the model, found by message attributes on the rig root
**Status:** Decided (author, 2026-11-12). Built and tested in Maya 2026 (`RigGroups` and `ParentMeshes` in `test_create_rig.py`).
`<namespace>:rig_all` is a plain transform that is the DAG parent of the rig's topmost input joints and topmost controls (a node whose DAG parent is not in its own set, so a skeleton with several roots gets several). `<namespace>:mesh_grp` is an empty transform under `rig_all`, and the model import parents the transforms it brings in to it (`rigmodules.groups.parent_meshes`). `rig_all` hangs on `rigRoot.allGroup` and `mesh_grp` on `rigRoot.meshGroup`, one message attribute each, like D38's layers.
- **Why:** an animator or exporter moves, hides or references the whole rig as one node, and the meshes need a fixed home. `inheritsTransform` is off for joints and controls, so reparenting them under an identity group changes no result.
- **Locked and hidden:** both groups lock and hide translate, rotate and scale (the nine channels, not the compounds) and keep `visibility` keyable. Queued as MEL on the modifier like D40, so undo and redo replay it.
- **mesh_grp is a second attribute, not a name lookup:** the author asked only for `allGroup`. `meshGroup` was added so the import tool finds the group by connection, never by name (D25's rule for tools).
- **Names must be free:** the build checks both names with the module and joint names, so a second rig variant built into a namespace that already holds `rig_all` fails in the read phase and builds nothing. Joint names already forced this, because input joints keep their names. If variants should share one `rig_all`, that is a change to this entry.
- **Consequence:** `rig_all`, `mesh_grp`, `allGroup` and `meshGroup` are public API. A rig's controls and joints are no longer top-level DAG nodes, so a tool that read a top-level parent breaks (`test_layout` did). mayadev's `assettools` should call `parent_meshes` after `add_meshes`: not done, that repo wasn't touched.

### D44. The art stages before the rig are file types with a status, not a second container
**Status:** Leaning (author and Claude, 2026-11-13). Not built. Full design: `asset-pipeline.md`.
The asset model (D29) extends upstream of the rig: sculpt, lowpoly, UVs, bakes and textures become file types with a `stage` (`source`, `intake`, `scene`, `export`), `inputs` and an optional `root`. Each part of each variant gets a status computed from stamps in the files (`missing`, `current`, `stale`, `unvalidated`, `unavailable`). The publish manifest is the engine equivalent.
- **Why (author's experience of a studio tool called the aggregator):** it mirrored the engine's data types, held its state outside Maya so work could not be saved without an export, checked mesh cleanliness late, broke skinning on art changes, and kept large source files in a parallel `highpoly` folder most people did not map.
- **Principles:** save never needs export. Source formats (ZBrush, Substance, Blender, Max) are tracked opaquely, never parsed. Status is computed, never stored, so there is no shared file to conflict. A source on an unmapped root is `unavailable` and never blocks a save or publish. Mesh identity is `meshId`, topology hash or closest point, never the name.
- **Rejected:** a container that mirrors the engine's types, a stored shared status file, silent topology fixes at intake, mesh name checks, and a required source root.
- **Mesh markup (proposed, needs sign-off; author, 2026-11-13: in C++ where there is a schema):** a mesh may carry a `usage` (`face_proxy`, `helmet`, gear parts such as arms and cape), identifying what it is for, with no defaults and no general enforcement. Engine-side `properties` (shaders, looks) are per face group, on a shading group, checked against the project's schema by a `core/` validator. Both live in a `meshMarkup` JSON attribute. Not part of any weight key.
- **Consequence:** three optional keys on file types in `project.json`, a weight-table transfer and content hash in `core/` (D35's "not built" transfer), and the rest in mayadev (D24, D30). No existing control, channel, template or file name changes. Open: face data, the skin load time, the neutral interchange format and the per-type budgets (`asset-pipeline.md`, section 15).

### D45. Face expressions come from blend shapes, and blend shape targets are asset data
**Status:** Leaning (author, 2026-11-13; revised the same day). Not built. Details: `asset-pipeline.md`, section 7.
Face expressions are driven almost entirely by blend shapes. A joint rig may be layered under them where needed (the skinning of the head and neck), but expressions do not come from joints or from a skinning solve, and there is no linear skinning decomposition step. A strong module-based joint rig is the alternative for a face that cannot use blend shapes. Blend shape targets are sparse delta files in the asset (a `blendshapes` file type keyed by `meshId` and topology hash, like weights, D35). They are edited in context, on a lightweight rig built from the template, with a simple pose library or test clip, and loaded by the rig at build. The face's animation interface is channel-only controls either way (D34).
- **Why (author's experience at a previous studio):** the face was blend shapes driving joints on UV pins, with a skinning result in the engine from a linear skinning decomposition: the worst of both worlds. Targets were non-export meshes stored in the rig's Maya file, which made imports slow and meant a rigger had to push every modeler edit. A rig is still wanted for seeing targets in context or in motion.
- **Rejected:** expressions from a mix of blend shapes, joints and a skinning solve. Targets as meshes in the production scene.
- **Consequence:** a face module goes through the gate (D12) with this as its constraint. The engine must take deltas, or a bake, for a blend-shape-first face (open). No existing name changes.

### D54. An asset holds skeletons, rigs and looks; a look replaces the variant
**Status:** Decided (author, 2026-11-16). Phases 2, 3 and 4 built (2026-11-16), the rest not. Full plan and phases: `rigs-and-looks.md`. Replaces D29's variants. `asset-model.md` describes what is built until phase 4.

A variant was a rig, so every outfit was its own rig. The author meant a look: meshes, textures, shaders and weights over one rig. An asset folder now holds `skeletons/{skeleton}/`, `rigs/{rig}/` (each naming its skeleton) and `looks/{look}/` (naming the skeletons its meshes bind to). A skeleton can have many rigs, and any rig of a skeleton can wear any of its looks.

- **Settled (author, 2026-11-16):**
  - The word is "look", not "variant", because the meaning changed. The default look is `default`.
  - Asset id tokens and skeleton, rig and look names are lowercase only. Uppercase is rejected, which replaces D29's "compare case-insensitively, store as authored".
  - One rig per namespace (`hero_body:`, `hero_face:`). Many rigs per asset (body, face, props).
  - The skeleton stays outside the rig, because a skeleton can have many rigs (a cinematic copy).
  - Skeleton identity is an automatic, deterministic hash of joint markup, parents and quantized rest transforms. Rejected: a user-updated version, which never got updated and changed on almost every edit.
  - Looks are whole bodies. Accessories are attachments. Rejected: parts-based looks, which were slow to aggregate and didn't fit together.
  - A look swap re-points the look's skinCluster inputs to the rig's joints by markup, with no bake or rebind.
  - Looks are chosen in the library browser. Assets, skeletons and rigs get a separate asset browser for riggers and modelers.
  - Identical-skeleton characters (NPCs) share one skeleton and its rigs, with no copied skeleton files. Their looks can live in look-only assets.
- **Answers to the plan's questions (author, 2026-11-16):**
  - Joint names are in the hash (the engine matches bones by name). Rest matrices are rounded to 1e-4.
  - The default namespace is always `{asset name}_{rig}`. Rejected: the asset name alone for a one-rig asset, a special case that renames the namespace when a second rig arrives.
  - The asset root merges into the rig root, which stores `assetId`. `assetRootModule` is removed.
  - An asset can hold many skeletons (`hero` holds body and face).
  - The template's `rigName` stays and must equal the rig folder name.
  - Skeleton exports live in `skeletons/{skeleton}/exports/`.
  - A copied rig names its `source` in `rig.json`, and the library browser lists the source's poses and animations. Saves go to the copy.
- **Built (phase 2, part 1, 2026-11-16):** `AssetId::isValidName` is the one lowercase name rule, and `AssetId::isValid` applies it per token. The template's `rigName` must pass it. Without the key it defaults to `rigTemplateName` in snake_case (`StringUtils::toSnakeCase`: `HumanRigTest` is `human_rig_test`), chosen by the author over requiring the key or deferring the rule. An explicit `rigName` is checked, never converted. The asset root's id compares exactly, and `StringUtils::equalsIgnoreCase` is gone. `RigTemplates/Human.json` is `human`. mayadev's `assetid` still accepts uppercase (proposed edit in `docs/mayadev.md`).
- **Built (phase 2, part 2, 2026-11-16):** `core/SkeletonFile` (the file and `skeletonHash`), `core/Hash64` (`Fnv1a64`, now shared with the weight file's `topologyHash`, whose values don't change), `maya/shared/SkeletonScene` and `cmds.saveRigSkeleton(*joints, file=path)`, which returns the hash. User page: `docs/skeletons.md`.
  - **Every marked joint counts** (author, 2026-11-16), marker joints (`export: false`) included, because the hash answers whether a rig and its looks belong together, and the rig is built on its markers. Rejected: export joints only, the engine's view.
  - The markup's `export` and `skin` flags are in the hash, since they are part of the markup and the weights depend on `skin`.
  - Rest is local to the parent, so an edit names the joint that changed and not everything below it. The parent is the nearest ancestor among the saved joints, so a group between joints folds into the child's rest.
  - No reader, update table or load command at this point (they came with phase 4, below). The rig build's `skeletonHash` stamp is phase 3.
- **Built (phase 3, 2026-11-16):** the scene side.
  - A namespace holds one rig: the read phase fails when the namespace already holds any rig root. The default namespace is `{asset name}_{rigName}`, resolved in the read phase after the template is read (`RigBuildInputs::rigNamespace` is optional, and `createRig` returns the namespace it used for the command's redo).
  - The rig root stores `assetId` and `skeletonHash`. `assetRootModule`, `RigTraversal::getAssetRoot` and the `assetRoot` connection are gone, and the id 0x00219 is retired. Old scenes with an asset root are not migrated (author, 2026-11-16), since no rigs need to survive.
  - The stamp is `skeletonHash` of `SkeletonScene::readSkeleton` on the build's input joints, read before the build moves them, so it equals what `saveRigSkeleton` returns for the same joints. `readSkeleton` repeats `collectMarkedJoints`' checks, which keeps one home for the hash. Rejected: hashing from the `MarkedJointSet`, a second reader of the joints.
  - `getRigInfo` drops `assetRoot` and adds `skeletonHash`. Its key was already `rigName`, so it stays. `RigInfo.variant` is `rig_name` (author, 2026-11-16, matching the key, over the plan's `rig`), `asset_root` goes and `skeleton_hash` is added.
  - Library `meta` (D51), format version 3 for poses and ControlAnims: `variant` is `rigName` and the caller's `skeletonId` is `skeleton`, with the rig filling `skeletonHash`. One update step, `renameVersion2MetaKeys` in `core/LibraryMeta`, serves both formats.
  - Weight files (D35), format version 2, with an update table: `skeletonHash` next to `topologyHash`, from the rig root that drives the influences (`RigTraversal::findSharedRigRoot`). `""` with a warning when they belong to no rig, an error when they belong to two. Rejected: hashing the influences themselves, which would differ from the rig's hash whenever a marked joint isn't an influence. A load records the hash and doesn't check it (author, 2026-11-16): the check comes with the look swap.
- **Amended (author, 2026-11-16, during phase 4's design):**
  - **`skeleton.json` is a skeleton's only stored form.** There is no skeleton `.ma`: saving serializes the joints and loading creates them from the file. Rejected: the plan's `.ma` with `skeleton.json` beside it, two formats for one thing.
  - **A model file is only meshes:** no joints, no skinCluster, no history. A look is its model plus its weight files, and a swap imports the meshes and loads the weights. Rejected: the plan's look file with meshes skinned to a copy of the skeleton, a second place a skeleton would be stored.
  - Signed off with these consequences: every joint of a skeleton must be marked (an unmarked one has nowhere to go); a load gives back only markup, name, parent, rotate order and rest (no radius, draw style, labels or groups between joints); rotation loads into `jointOrient` with `rotate` at zero and `segmentScaleCompensate` off; a stale stored hash is a warning.
- **Built (phase 4, RigModules part, 2026-11-16):** `deserializeSkeleton` and `skeletonUpdateTable` in `core/SkeletonFile`, `SkeletonScene::createSkeleton` and `cmds.loadRigSkeleton(file=path, namespace=ns)`, undoable. The reader recomputes the hash and warns when the stored one differs. A load fails, creating nothing, when a node in the namespace has a joint's name. The `rigMarkup` attribute is created in one place, `JointMarkupScene::queueAddMarkupAttribute`. A save, load and save gives the same file text, and a rig built on loaded joints stamps the file's hash (suite tests).
- **Built (phase 4, mayadev, 2026-11-16, branch `rigs-and-looks-phase4`):** the file model: project format 3 and its update step (only default paths are replaced, an edited `{variant}` path fails the load by name), `asset.json` version 2 (no `skeleton`), `rig.json` and `look.json`, `Asset.skeletons`/`rigs`/`looks`, the registry and publishes per rig and look, the library per rig (Shared is the source rig's), New Rig (writes `rigName` into the copied template), New Look, Load Skeleton, mesh-only Save Model, `build_rig(asset, rig, look)`. A built rig doesn't record its look until phase 5, so the weight tools take the look. Looks from another asset, a hash in the bone map and the attachment parent key in `rig.json` are left for later phases.
- **Built (phase 5, RigModules part, 2026-11-17):** the `lookRoot` node (`maya/nodes/LookRoot`, `MTypeId` 0x002190, no `compute`), connected from the rig root's new `look` message, with `assetId`, `lookName`, `publishVersion` and a `lookMembers` message array, and `cmds.setRigLook` (`maya/shared/LookScene`, `LookSwap`). `getRigInfo` gains `look` (null or `{assetId, name, publishVersion}`) and `RigInfo` gains `look: LookInfo | None`. Decided with the author:
  - **The swap splits at the asset boundary.** mayadev imports the look's meshes into the rig's namespace and passes them with their weight files (`mesh` and `file`, multi-use), so RigModules reads no asset paths (D24). Rejected: a command that takes a model file and a weights folder, which would break D24 and import a file inside an undoable command.
  - **One undo step.** Each mesh's `SkinWeightLoad`, then one `MDagModifier` that deletes the previous look's members (MEL `delete`, so their history goes too), names each new mesh after its weight file's `meshName`, and creates or updates the `lookRoot`. A failed command takes back whatever ran.
  - **The lookRoot owns its nodes through a message array**, not a set: a swap deletes exactly the members, so a mesh the animator added is never deleted. Materials a look brings are not members and stay (known gap). Meshes are matched to files by `meshId`, never by order or name.
  - **The hash check is an error, `ignoreSkeletonHash` a warning.** `SkinWeightLoad::prepare` compares the file's `skeletonHash` with the rig that drives the influences. A file with `""` loads with a warning (it can't be checked), and joints in no rig are not checked. `loadRigSkinWeights` and `setRigLook` both take `ignoreSkeletonHash`. `setRigLook` can also take the look's and the rig's `skeleton.json` (`describeSkeletonDifferences`) so the error names the differing joints.
  - **No `meta` on a look yet** (author): the library browser's Looks kind doesn't need tags or a description until it has them, and `look.json` would then get a D33 update step.
- **Built (phase 6, mayadev only, 2026-11-17, branch `rigs-and-looks-phase5`):** listing looks that aren't synced. No RigModules change.
  - **Two calls on `SourceControl`:** `list_folders(path)` (child folder names, synced or not, `None` for the default adapter) and `sync(path)`. `Asset.all_looks()` returns `AssetLook(name, local)` for every look and falls back to the local scan, with a logged warning, when the adapter raises, so a server that is down never empties the library. `Asset.looks` stays the local scan: callers that read a look's files can't be handed a look that isn't there. Rejected: changing `Asset.looks` itself.
  - **Choosing an unsynced look syncs it.** `assettools.apply_look` syncs before it touches the scene, then runs the usual checks (the look's `look.json` must name the rig's skeleton), so a failed sync or a look that doesn't fit changes nothing. An unsynced look is listed by name only, because its fit can't be known until it is synced.
  - **Not built:** the Perforce adapter and the library window's Looks tab (author, phase 6): tested with a fake adapter.
- **Rejected:** one asset per skeleton, rig and look, named by id (option B). It made the hero about eight asset folders and still ended in large look folders. Also rejected: a master list of an asset's looks, which brings back D29's shared-file edit. Listing unsynced looks asks source control instead.

Attachments (an attach node, cross-rig constraint drivers) and the face parameters node go through the gate later.

### D55. An attachment follows another rig through `parent:` ids, with no attach node
**Status:** Decided and built (author, 2026-11-17). Design: `attachments.md`. User docs: `docs/attachments.md`. Phase 7 of D54.

A face, cape or prop is a rig of its own that follows another rig. Its template names sockets of the parent rig as `parent:module.socket`, in a `parentStructure` value or a constraint driver, and `createRigFromTemplate(..., parentRig=rigRoot)` resolves them in the parent's namespace. A control driven only by `parent:` sockets is hidden, locked and left at rest. The rig root records the parent (`parentRig`, from the parent's `attachments`), `getRigInfo` returns `parentRigRoot`, and the read phase lists every missing socket at once (D17).

- **Why:** the plan (D54, section 7) expected an attach node holding a child-plug-to-socket mapping. A constraint driver already resolved `namespace:module.socket` (D31), so the only gap was the parenting pass and the validation, which knew one rig. Extending them adds no node, no `MTypeId` and no `compute`, so the 20-rig frame time (D36, already under target) is not spent. The template lists what it needs, so there is no separate mapping file to keep in step.
- **Rejected:** a new attach node (a node type, evaluation cost, a contract test, nothing it would do that the connections don't); constraints alone (one constraint per control, no whole-hierarchy follow); controls omitted from the attachment when attached (it could not be detached, and its control set would change with its parent, which breaks pose and animation names); a separate attach file (a format, a version step and a second place for names).
- **Consequence:** the follow is written at build time, so detaching or changing the body is a rebuild. A look that spans a rig and its attachment is applied with one `setRigLook` per rig, by the tool. The mayadev side (`rig.json` `parent`, build-and-attach, `apply_look` for a spanning look) is built on mayadev branch `attachments-phase8` (stacked on `rigs-and-looks-phase5`), not yet committed or merged (`attachments-mayadev.md`, section 9). RigModules gained `rigmodules.skinweights.read_file_skeleton_hash` for it. Public names added: the `parent:` prefix, `parentRig` (flag and rig root attribute), `attachments` (rig root array), `parentRigRoot` (`getRigInfo`), `RigInfo.parent_rig_root`. Measured: 20 complex rigs at 25.9 fps alone and 25.6 fps with 80 attachments (D36's target is 30).

### D58. One naming convention for joints, controls, modules and constraints
**Status:** Decided (author, 2026-11-18). Built and run in mayapy 2026: the class, the build, validation, mirroring, the command and its undo.

Every name is `<camelCaseName>_<##>_<L|R|M>_<JNT|CTRL|MOD|CON>`: `upperArm_00_L_JNT`, `upperArm_00_L_CTRL`, `fkChain_00_L_MOD`, `armSpace_00_L_CON`. The rules live in one Maya-free class, `core/NamingConvention` (`parse`, `format`, `controlName`, `fromUsage`, `swapSide`). Page: `docs/naming.md`.
- **Why (author, 2026-11-18):** one predictable form that carries side, index and kind, so tools and animators read a name without lookups, and mirroring is a side-letter swap. The old forms (`arm_jnt`, `arm_ctrl_l`, `fkchain_1`) had a different shape for each kind and a side suffix that some kinds lacked.
- **Joints are named by the author of the skeleton, and a name outside the convention is an error** (author, 2026-11-18, over a warning) in the build's read phase. The build keeps joint names as before. Controls are built from the joint name (the joint's base and index, the module's side, `CTRL`) or, with no joint, from the usage (`layout_0` gives `layout_00_M_CTRL`, `armIK` gives `armIK_00_L_CTRL`). A module's or constraint's name in a template must parse, and a module's side letter must equal its `side`.
- **The layout is `layout_00_M_MOD`** (author, 2026-11-18, over keeping `layout` reserved). Templates address `layout_00_M_MOD.end`, so the layout needs no special case in the naming rules.
- **Constraints got a fourth kind, `CON`.** The author asked for joints, controls and modules. Constraint names are mirrored by a side swap (D28), so they need a side, and a fourth kind was cheaper than a second naming rule. `createRigConstraint` without `name` gives the control's name with `CON` instead of `<control>_space`.
- **Command:** `renameRigNodes` renames the nodes passed, or the selection, in that order (index from `startIndex`, 0 by default). The kind comes from the node type (`NamingScene::getKind`). It checks every target before the scene changes and renames through temporary names, so renumbering nodes among themselves works. It reads the selection in selection order, which needs Maya's `trackSelectionOrder`. It fails on a selection of more than one node while that is off, and does not change the user's preference (rejected: turning it on, since it is a user setting). `query` returns the parts of a name. Python: `rigmodules.naming` (`rename_nodes`, `parse`), thin over the command so the rules stay in C++.
- **Rejected:** a `names` list flag on the command (one base per node), since `base` plus order covers renumbering and the author asked for order-based indexes. Checking a joint name's side letter against its markup `side` (more failure for a cosmetic mismatch, left to the author's tools).
- **Consequence:** every control, module and constraint name changes, so rigs built before this must be rebuilt (no migration, D24), and saved pose, animation and shape files are keyed by markup and so are unaffected. Golden snapshots were regenerated, and the template module names, constraint names and socket ids in every fixture and doc changed. The suffix constants `JointSuffix`, `ControlSuffix` and the side suffixes left `RigNaming`, and `getSideSuffix` and `getSideFromSuffix` left `Side`. Selection set names still follow the module name, so they read `arm_00_L_MOD_joints_set`. mayadev call sites that build or parse these names must change.

### D61. The Asset Editor is a dockable asset context over files, markup and shapes
**Status:** Decided (author, 2026-11-19). Phases 1 to 3 built on mayadev branch `asset-editor`, not merged, and not checked in a GUI Maya. Design and what differs: `asset-editor.md`.

One window where a modeler or rigger sets the asset they work on and creates, saves and loads its files, edits joint markup across a selection, and edits control shapes across a selection. It follows D49 to D51.

- **The context:** `AssetContext` holds the asset id and the skeleton, rig and look. It changes only by an explicit action, never on file new, open or save, and closing the tool removes every callback it registered and clears it. The last asset prefills the next open.
- **Menu tools:** when the editor is open they offer its asset instead of asking for an id, after a confirm.
- **Files:** rows come from the project's file types and the handler registry, so textures, shaders and tracked files appear by adding a file type and a handler.
- **Rejected:** role presets, a lazy tree over the projects root, editable control markup (the build owns it, D25), template hints (deferred to the template tool).
- **Consequence:** mayadev only. No RigModules node, command or name change, no D36 impact.

### D68. A look build never fails over weights: marked meshes with no file bind rigidly to the topmost skin joint
**Status:** Decided (author, 2026-11-21). Amends D54's look swap. Design: `looks.md` ("Meshes not skinned yet"), mayadev `apply_look`.

A look's model can hold meshes nobody has skinned yet (props, attachments in progress). Before this, mayadev's `apply_look` deleted a marked mesh with no weight file and failed the whole build on a weight file whose mesh was missing, which left the rigger nowhere to do the skinning.

- **RigModules:** `setRigLook(rigidMesh=[...])` takes meshes with a `meshId` and no file. `LookSwap` makes in-memory weights (core `setRigidSkinWeights`: every vertex 1.0 to one influence, the rig's skeletonHash) and loads them through `SkinWeightLoad`, so undo, membership and deletion on the next swap are the same as a file mesh. A rigid mesh keeps its name.
- **Which joint:** the topmost skin joint, core `findTopSkinJoints` (a `skin` joint with no `skin` ancestor). Several is a warning and the first is used. None is an error. The root is the usual answer.
- **mayadev:** every marked mesh with no file goes to `rigidMesh` with a warning. An unmarked mesh is left in the scene, untracked, with a warning, because marking is how a mesh joins a look and binding every mesh would pull in blend shape targets. A weight file with no mesh is a warning, not an error, and points to Load Skin Weights by Name, which matches files to meshes by `meshName` and restamps the mesh's `meshId` from the file. A look that spans several skeletons (D55) keeps deleting meshes no rig has a file for, because there is no rig to bind them to.
- **Why meshIds drift:** the id lives on the scene node. Marking a mesh in a scene that was not loaded from the model file (a re-import, the art source) gives that node a new id. Nothing re-stamps an id behind the rigger's back. The name load is the repair.
- **Changed skeleton (2026-11-22):** `ignoreSkeletonHash=True` also covers a file that can't load on the changed skeleton (a joint it names is no longer marked, or the topology changed). `LookSwap::prepare` demotes that mesh to a rigid one with a warning, so the look still applies and the mesh is tracked, ready to skin and save over the file. Without the flag it stays an error. The Asset Editor's Build Rig has the matching checkbox (mayadev). Rejected: a separate flag, and retrying the whole look rigid on any failure, which would throw away the files that do load.
- **Rejected:** creating weight files on disk for unskinned meshes (files nobody made, in source control), matching by name inside the build (silent, and it would hide the drift), deleting unweighted meshes (the old behaviour).
- **Consequence:** one new `setRigLook` flag. No node, attribute or name change. No pose, animation or export impact: a rigid mesh exports skinned to the root until it is painted. No D36 impact (build time only).

### D69. Meshes are named by the convention too, with the suffix `GEO`

**Status:** Decided (author, 2026-11-22: "rename with suffix based on type"). Built.

- **What:** a new `NamingConvention::Kind::Mesh` with the token `GEO`, so a mesh is `<camelCaseName>_##_<L|R|M>_GEO` (`body_00_M_GEO`). `renameRigNodes` takes the transform of a polygon mesh (the shape under it, skipping a skinned mesh's intermediate shape, decides) and names it by that kind, with the same base, side and start-number rules as the other kinds. The query returns kind `Mesh`. The Asset Editor's Naming tab (mayadev, D61) needs no change, since it hands nodes to the command.
- **Why in the convention and not a looser mayadev rename:** D58 put the rules in one class so nothing else builds or parses a name. A second mesh-only rule in mayadev would be the thing D58 prevented. The cost is one enum value and one detection branch.
- **What it does not do:** nothing requires a mesh to be named this way. The build, the template validation and the look build do not check mesh names, and a module or constraint name ending in `GEO` is still refused (template validation asks for its own kind). Skin weights match by `meshId`, never by name (D35), so a rename cannot break weights. A look build names its meshes after the weight file's `meshName`, so a rename lasts across a rebuild only after the weights are saved again. A `rigidMesh` keeps its name.
- **Rejected:** a catch-all kind for any other node (a group, a locator, a camera: no one asked, and each needs its own suffix and detection, add one when a case appears), renaming the shape node (Maya names a shape after its transform, and tools find the transform).
- **Consequence:** public API grows by one kind and one suffix. No existing name changes, so no pose, animation or export impact. No D36 impact. mayadev: no call site breaks (it passes the leaf name to `rigmodules.naming.parse`, which now also reads `_GEO` names).

### D70. A look build survives a changed skeleton, mesh or weights; strictness moves to the publish gate
**Status:** Leaning (author's direction 2026-11-22, not signed off as a whole). Amends D54 (the skeleton hash gate) and D68 (rigid fallback, the `ignoreSkeletonHash` flag). Design: `asset-build-fallbacks.md`. Nothing is built.

While an asset is in progress its skeleton, meshes and weights change independently, and a build that fails over the mismatch leaves nothing to repair.

- **Decided direction (author, 2026-11-22):** a changed mesh gets its weights by **barycentric transfer** (closest point on the old surface, the triangle's three weight rows blended by barycentric coordinates), not nearest vertex. The "Ignore skeleton changes" checkbox is removed, so the fallback is always on.
- **Proposed, awaiting sign-off:**
  - The skeleton hash decides status, never success. A file loads whenever its topology matches and its influences resolve. An unresolved influence folds into its nearest resolvable skin ancestor.
  - A per-mesh ladder (`loaded`, `folded`, `transferred`, `rigid`) and a per-mesh report returned by `setRigLook`. Mechanism is in RigModules, policy in mayadev.
  - The weight file (version 3) stores its bind-pose surface and each influence's skin parent, so transfer and folding need no other file. Rejected: finding the old model by stamp in local versions or a publish (not shared across machines, absent in a draft).
  - Draft (no publish) and checked out (a publish exists) build the same way. The difference is at the gates: the publish gate refuses any non-`loaded` mesh, and a checked-out skeleton is checked for breaking changes (a removed joint, a changed markup identity or parent) against the baseline. Rejected: a stricter build for checked-out assets.
- **Consequence:** `ignoreSkeletonHash` is removed from `setRigLook` (and `loadRigSkinWeights`, pending open question 4 in the design page), which breaks mayadev callers, listed in the design page. A new weight file version with a version step (D33). No impact on poses, animation or exports.
