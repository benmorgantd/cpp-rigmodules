# Decisions: mayadev tools and UIs

How the sibling mayadev repo's tools relate to RigModules: menu tools, the launcher, the Qt view-models, the active rig panel and the library browser. Part of the decision log: the Index and the open items are in [`../decisions.md`](../decisions.md). Entries are in number order.

### D47. mayadev menu tools name a function by readable id, and their files are checked and versioned
**Status:** Decided and built in mayadev (2026-11-14). Phases 1 and 2 landed together, because phase 2 keeps every phase 1 fix. Verified in plain Python, in mayapy against a plugin build and offscreen Qt; the real menus and the editors were not driven in a GUI Maya. Details and the differences from the first design: `tool-registry.md`.
mayadev's tool registry and menu layouts stay plain JSON. Phase 1 fixes the load, save and menu build bugs on the current format. Phase 2 (format version 2): a tool is a readable `id` and a `call` (module, function, keyword arguments) in place of a `script` string. Dataclasses in Maya-free `bmaya.core.tool_registry` represent the files. A read-only check pass reports every problem at once before anything is built. Each file carries a `version` with an update table (the Python form of D33). One `build_menus` serves both startup and reload.
- **Why:** a script string was checked only when clicked (the `joints` typo shipped that way), ran in a module's globals, and gave tracebacks with no tool name. A call keeps menu items to one line of intent, and it can be checked without running it. Readable ids make layouts reviewable, and they give tests a stable key, which today they get from display names.
- **Rejected:** keeping a `script` escape hatch. Decorator-based tool discovery, which hides the menu contents in code. A version per tool: a tool's contents are content, and only the file shape is versioned. pydantic and JSON Schema. Keeping unknown keys: they are an error.
- **Consequence:** tool ids are public, like control names. Version 1 to 2 is a one-time migration script, not an update step, because it reads two files and needs seven new functions. `short_name` stays for the planned shelf view, and must be unique once the shelf is built. Answered 2026-11-14:
  - The inline scripts become functions in `assettools`, `posetools` and `rigging.joint`.
  - A menu with a plugin is built only while that plugin is loaded, so the dev tools move to the bmaya menu (approved).
  - Phase 1 does not change the `exec` globals.

### D48. One launcher starts and ends Maya: `python/mayalaunch`, beside `rigmodules`
**Status:** Decided and built (author, 2026-11-14). It first lived in its own repo, and moved into this one the same day (author: no extra repo, and mayadev still depends on RigModules and never the reverse). Verified: its tests (19, in the suite, plain Python plus one real mayapy round trip), the full suite through `RigTests.cmd`, a forced `--timeout` stop, `ViewportGallery.cmd` in a real Maya window, a mayadev batch job in mayapy, `perf_scenes.py check` and `generate_control_shapes.py` (its output is unchanged). `perf_scenes.py` `human`, `complex`, `bench`, `gui` and `profile`, and `fbx_spike.py`, were not run after the change.
`mayalaunch` is plain Python with no dependencies, a package of its own so that `rigmodules` keeps its rule of no environment variables and nothing but rig API (D24). It finds the Maya install (`MAYA_LOCATION`, else the Maya 2026 folder), builds a child environment (`MAYA_DISABLE_CER`, `MAYA_SKIP_USERSETUP_PY`, `TEMP` in the run folder), runs a mayapy or a GUI Maya as a watched child with a timeout (the process tree stops by pid, then leftover crash reporters close), copies the plugin before loading it, and inside a mayapy starts standalone with its output in a log and ends with `uninitialize` then `os._exit`. `run_tests.py`, `perf_scenes.py`, `generate_control_shapes.py`, `fbx_spike.py` and the viewport gallery call it, and so does mayadev's batch framework.
- **Why:** the same launch and teardown code existed in six places here and in mayadev's `MayaBatchEnvironment` and `run.bat` files, and each had learned different lessons (only `run_tests.py` closed crash reporters, only `perf_scenes.py` knew the `-command` quoting rules). A hung Maya had no timeout anywhere. In this repo, mayadev already reaches RigModules' Python through `RigModules.mod`, so it reaches `mayalaunch` the same way.
- **Rejected:** building the tests on mayadev's `base_batch_framework.py`: it runs a job over scene files inside the current process and never starts mayapy, so it has no crash isolation, tiers or streamed outcomes, and RigModules can't import `bmaya` (D24). A separate `mayalaunch` repo: a third thing to keep on disk and to find from two repos. A copy per repo with a sync test. A git submodule.
- **Consequence:** `perf_scenes.py gui` and `profile` take `--maya-dir` in place of `--maya` (the path to `maya.exe`). `run_tests.py` gained `--timeout` (default 900 s). `ViewportGallery.cmd` now starts `testsiewport
un_gallery.py` in mayapy. mayadev's `BaseBatchEnvironment` takes `root_dir`, `run_suite` takes `open_report`, and a bare mayapy running a batch job needs `python\` on `PYTHONPATH` (mayadev's batch files set it from `RIGMODULES_ROOT`). The launcher's tests add about 30 s to the suite's run.
- **Not done:** mayadev's `run.bat` files still call mayapy directly, which is one line each, and a mayadev batch job still runs all its items in one process, so a crash ends the batch. Per-item child processes are the next step if that is wanted.

### D49. mayadev UIs are thin Qt views over headless view-models and workflows
**Status:** Decided (2026-11-14). Phase 1 built the same day on mayadev branch `ui-phase1` (not yet merged): verified by mayadev's suites (305 tests), the startup smoke test and a GUI Maya started through `mayalaunch`. Clicking the menu tools in a GUI was not done. Phase 2 (the `RegistryEditSession`, `host.py`, `menus.py`, `SignatureForm`) built the same day on the same branch, checked by the suites and a GUI Maya, with the author's `userSetup.py` and a person using the editors not checked. Phase 3 is not built. Design, phases and the as-built differences: `mayadev-ui.md`.
mayadev's UIs follow the author's rules (2026-11-14): no `.ui` files, model / view-model / view, reusable and fast, not tied to Maya where avoidable, the least code in the UI, every pipeline action callable from mayapy, imports only from `core` to `maya` to `maya_ui`, and Qt dialogs, never `cmds` ones.
- **Layers are wired by a registration pass** (author's suggestion). A lower layer declares a slot (log writers by level, the prompter, file handlers, reload hooks) with a default that works headless. `bmaya.maya.startup.register()` and `bmaya.maya_ui.startup.register()` fill the slots, and `userSetup.py` and batch jobs call them. `bmaya.asset.handlers` already works this way.
- **View-models** are plain classes in `core` or `maya` with `Event`s (`core/observable.py`), not `QObject`s.
- **Questions go through a `Prompter`.** Menu tools ask through a protocol in `core`: Qt dialogs in a GUI session, a scripted prompter for tests and batch, and a default that raises in mayapy.
- **Maya UI calls stay in the host.** Only `maya_ui/host.py` (docking) and `maya_ui/menus.py` (the main menus) call Maya UI.
- **Forms come from dataclasses** and type hints.
- **Moves and renames:** `bmaya.asset` becomes `bmaya.core.asset`. The `*_ui` menu entry points in `bmaya.maya` become `*_interactive`.
- **Why:** reading the code found `maya/devreload.py` importing `maya_ui`, `core/log.py` importing Maya, 17 `cmds` dialog calls and their untested workflow branches in `maya/assettools.py`, one export path (capturing a clip without an asset folder) reachable only through a dialog, `.ui` loading in `qtbase.py`, and editor windows holding their own state.
- **Rejected:** Qt signals in view-models, which would make `core` need PySide6. A binding library. Windows generated from data, a `.ui` file by another name. `cmds` dialogs. Passing every service as an argument, or a `maya_ui` wrapper per interactive tool to pass the prompter. View-models in `maya_ui`. A compatibility module at `bmaya.asset`.
- **Consequence:** tool ids stay as they are. The renamed functions' `call`s change in the registry in the same change. The `Prompter` protocol and each slot are interfaces between layers. Every slot is filled only from a `startup.register()`, and a test pins that. As built, the file handlers stay registered by each tool rather than by startup, so a mayapy job without startup still has them, and `bmaya.maya_ui.widgets` (`DataclassForm`, with `FieldEditor`, which phase 2 turned into `field_widget`, `show_value` and `read_value`) came forward from phase 2 to replace the last `cmds.layoutDialog`. Phase 2 changed no tool id or menu layout: the two editors' `call`s name `bmaya.maya_ui.menus` now.

### D50. The active rig panel is a launcher over the existing pose tools, with one new query for spaces
**Status:** Decided (2026-11-14: the author answered the open questions). Phases 1 (tracker `changed`, plain pose functions, `RigPanelSession`), 2 (the window, the registry tool and the `panels` submenu) and 3 (the space row, with `getRigControlSpace`) built on mayadev branch `ui-phase1`, as-built differences in `active-rig-panel.md` sections 12 to 14. The out-of-date line is not built. Design and phases: `active-rig-panel.md`.
**Author's answers:** a space switch never keys by default, with an optional Key checkbox (`set_space(label, key=False)` carries it to mayapy). The panel docks as the host does, beside the Attribute Editor or the Outliner. The panel and the library browser are two panels and two tools. `changed` lives on the tracker class. There is no "key selected controls" button. The panel warns when the rig is out of date, from mayadev's out-of-date check (`asset-model.md`, not built), and never updates a rig.
The first panel of phase 3 (D49). It shows the active rig, selects controls by module and side, runs the pose tools (zero, mirror, flip, key) and switches the selected control's space.
- **View-model in `bmaya.maya`** (`RigPanelSession`), no Qt, with `Event`s. The view is `bmaya.maya_ui.rigpanel`, docked through `host.show`.
- **`ActiveRigTracker` gets a `changed` Event** and a public `refresh`, so the panel and the later library browser follow the active rig without polling.
- **The controls are read once per rig change** (`get_rig_controls`), not per selection change. The panel lists no controls (author, 2026-11-14: the Outliner does that, and a copy would need its native selection, icons and spacing). The Select section has a button per module and side, a click selects and ctrl or shift adds, and nothing follows the viewport selection. The sections are labelled and fold.
- **`posetools` gets plain functions** with explicit controls beside the `_interactive` ones.
- **RigModules gains one read-only query** for a control's space switch: a new command `getRigControlSpace` (built 2026-11-14), over adding `spaces` to `getRigControlInfo`, because no Python query found a control's constraint, labels or current space. `rigmodules.query.find_control_space` wraps it.
- **Rejected:** a channel box copy, two-way selection sync, selection sets as the control source, a control tree or a custom tree model, keying a space switch by default, a panel that updates a rig itself, and `ListModel` in this panel: it comes with the library browser.
- **Consequence:** no node, attribute or name changes in RigModules, no D36 impact. One new command and one new Python function.

### D51. The library browser is a searchable view over control data, with sources, masks and file metadata
**Status:** Decided (2026-11-14: the author answered every question and signed off). Phase 1, the RigModules side, is built (`library-browser.md` section 12c), and so are phase 2, mayadev headless (section 12d), and phase 3, the window (section 12e). Publish to Approved and thumbnails (phases 4 and 5) are not. Design and phases: `library-browser.md`.
The second panel of phase 3 (D49, D50). It lists ControlPoses and ControlAnims from three sources (Approved: the asset's folders; Shared: the skeleton asset's; User: the animator's own, where Save goes by default), searches name, tags and metadata, and applies an entry to the selection, the whole rig or a mask (a filter by module, side and usage, never by name). Saving is one field and Enter.
**Author's answers:** the skeleton asset's folders are a Shared source. No thumbnails in the first build. Mirror the data first, not the rig. An animation applies at its own start frame. Files are named `<name>.controlanim.json` and `<name>.controlpose.json`. The User library is `<projects root>/user/<login>/animlibrary/<asset id>/...`.. Metadata is data in the file, editable after save, and includes `status` (scratch, review, final), `category` (free text) and `rigRegions` (lower body, upper body, head, hands, declared in `project.json` under `rig`). Per-shot sources wait for a shot concept. A 3D preview on a skeleton with a proxy mesh is a later idea: a `<name>.preview.json` joint sidecar paired by `meta.skeletonId`.
- **Layers:** sources, listing, search and masks in `bmaya.core.asset.library` (no Maya), `LibrarySession` in `bmaya.maya`, `ListModel` in `maya_ui/widgets.py`, `LibraryBrowser` in `maya_ui`. A second tool beside the rig panel (D50).
- **RigModules changes:** a `meta` block (asset, variant, template, skeleton, plugin version, created, author, tags, description) in both file formats (version 2, with D33 update steps), `getRigDataFileInfo` (a batch read for the index), `setRigDataFileMeta`, a `mirror` flag on `loadRigPose` (a data transform sharing its channel rules with the flip and `mirrorRigKeys`), and the `.controlanim.json` and `.controlpose.json` names. Chosen over parsing files in mayadev, because the format and its update steps live here (D24).
- **Rejected:** a folder per face or race or rig type, name filters, a metadata sidecar, preview on selection, a background mirror thread (the Maya API is not thread safe), load-then-flip mirroring, enforcing approval in the browser.
- **Built (phase 1):** `meta` as one JSON flag on the two save commands (not a flag per field), `getRigDataFileInfo(rigRoot, file=[...])`, `setRigDataFileMeta(file=, meta=)`, `loadRigPose(mirror=)`, `rigmodules.library`, both formats at version 2 with a version 1 update step. The rig fills `assetId`, `variant`, `pluginVersion` and `created`. The caller passes `template` and `skeletonId`, because the rig stores neither.
- **Built (phase 2, mayadev):** `bmaya.core.asset.library` (sources, listing, an index cached by path, modified time and rig, search, masks, rename, delete, copy), `LibrarySession`, `ListModel` (a table model, so the Details view shares it), the vocabularies in `project.json`, the `user` folder reserved in `assetid` and the registry, the `.controlpose.json` and `.controlanim.json` names with legacy files still read, and Save Pose and Save Animation writing to the user's own library. Open: RigModules' `core/AssetId` doesn't reserve `user` (`docs/mayadev.md`).
- **Built (phase 3, mayadev):** the window (`maya_ui/librarybrowser.py`) over `LibrarySession`: one table as List or Details, a Filter menu whose picks write search terms, source chips, scope with the rig's, the team's and the user's masks, Apply by double click or Return, Save by Enter, a context menu per source, the vocabulary warnings, and `TagsEdit`. A GUI Maya showed `addAction(text)`, `addMenu(text)` and `widget.style()` handing back deleted objects, which the offscreen suite did not, so the window builds its actions explicitly and `tests/gui/librarybrowser/run.bat` checks it docked.
- **Consequence:** no node, attribute or name change in RigModules, no D36 impact. Two commands, one flag on each of three commands, and a format version. Thumbnails and a grid view are phase 5.
