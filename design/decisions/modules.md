# Decisions: Modules

The module nodes and how they are designed: two-bone IK, Ribbon, Limb, control placement, template keys, module naming, and what comes after the limb. Part of the decision log: the Index and the open items are in [`../decisions.md`](../decisions.md). Entries are in number order.

### D46. After the IK limb: a pose-driver with a marker spec, then the face module, and overlap only on request
**Status:** Leaning (author, 2026-11-13). Not built. Details: `ideas/module-directions.md`. The IK limb stays next (2026-11-10).
The next modules are a stateless pose-driver (cone, distance or RBF solves over world matrices, defined in JSON) with a marker spec for the engine, then the face module (D45) with a channel map and a connectivity rules file, and overlap only as a stateless approximation if animators ask. Stateful simulation stays engine-side.
- **Why (author's production experience):** secondary behaviour such as high collars and correctives is driven by pose and does not need state. Velocity-based overlap needs frame history, which breaks scrubbing and parallel evaluation (D36).
- **Rejected:** a stateful simulation module. A live node for face connectivity (the driven channel would be unkeyable, so rules are data applied by an animator-facing tool). Building the system around swappable gear parts: the plug and socket model limited design continuity and paid off mainly for microtransactions.
- **Consequence:** each module goes through the gate (D12). Open: whether the engine evaluates pose-driver definitions, and whether a marker is an export extension or a module.

### D52. Two-bone IK: a `TwoBoneIk` limb with a matched IK/FK switch and module-owned spaces
**Status:** Decided (author, 2026-11-15: three rounds of answers). All eight phases built 2026-11-15 (the forward module, the inverse, the matched switch `setRigIkFkBlend` and `setRigControlSpace`, the perf rig and `bench`). The gate's `bench` result is below target (D36: 27 and 22 fps for 20 rigs, 1.6 to 1.7 times the floor on 50): the limbs' cost is node count, not the solver (1.4% of node time), and the author accepted the cost (2026-11-15, D36). The rig panel's IK/FK controls are mayadev work, proposed and not built. Design and build phases: `two-bone-ik.md`.
The IK limb (2026-11-10) is a two-bone limb: exactly three joints, for arms and legs. One-bone IK is `Aim`, and three or more bones or spline IK would be their own modules.
- **Controls:** an FK chain whose start control also moves the IK root (translation only, its rotation does nothing to the IK chain), an IK handle, a pole and a channel-only settings control. The handle, pole and settings take their markup and rest from three non-export marker joints, selected in `moduleArgs` like Aim's `target` and `up`.
- **Channels:** `ikFkBlend` (default 1, IK, for every limb), `stretch`, `soft` and `pin` (0 to 1), `roll` on the handle (`mirrorNegate`), and a module-owned `space` on the pole (`Parent`, `Ik`). Soft IK is in v1. **Amended 2026-11-26 (author):** the pole's `space` defaults to `Ik` (1), its rest and build value, for TwoBoneIk and Limb, so a new limb's pole follows the hand. The label order stays (append-only, D34): only the default moved. Saved poses and clips that store `space` keep their value. Ones without it, and `zeroRigControls`, now give `Ik`, and a rig built before this keeps `Parent` until rebuilt. FK controls keep translate, rotate and scale so FK can reproduce a stretched or pinned pose. Controls hide by blend.
- **No pop:** the node publishes the control values that match each side to the current pose (`fkMatchLocal`, `ikMatchLocal`, pulled only by tools), and `setRigIkFkBlend` writes them and sets the blend. A raw `ikFkBlend` change doesn't match, like a raw `space` change (D27).
- **Module-owned spaces** are a general concept: a `space` enum a module reads itself, with static labels and the module's own `attributeAffects`, reported by `getRigControlSpace` (a new `module` key) and switched by `setRigControlSpace(control, ...)`, which matches either kind of space (D27), a module's through a `ModuleDescriptor::spaceDelta` hook. Named for the control because the space belongs to the control, not the module. The pole's is the first. `rigConstraint` can't give the pole an IK handle space, because the module's own socket as a driver is a cycle (D17).
- **The settings control** follows the `parentStructure` socket of the module's first child plug (the chest for an arm, the pelvis for a leg), through an internal child plug the template can't name, so a constraint on `start` doesn't carry it.
- **Inverse (amends D41, built 2026-11-15):** the contract gains scalar channels, a vector like its other fields: `ModuleDescriptor::inverseChannels` names them (channel, slot, default) and `ModuleInverseInput::channels` carries their values in internal units, filled from the sidecar or the rig's current value so the inverse uses the value the forward solve will. FkChain, Aim and Layout list none. The handle's distance is a bisection on the forward reach, and the pole a quadratic, so soft, stretch and pin are exact in any mix (`TwoBoneIkSolve::computeTwoBoneIkInverse`, moved from `MathUtils` on 2026-11-20). The match outputs will call the same inverse inside `compute()` and allocate, the one exception to the allocation-free rule, accepted because only tools pull them.
- **Rejected:** FK values as offsets from IK (FK poses stop transferring, and the other direction is a cycle), a `poleFollow` slider beside a constraint enum, relaxing D17 to per-slot dependencies, derived usages with a computed pole, a pole-only `setRigPoleSpace` and a `setRigModuleSpace`, a template-named settings child plug, settings following `start`'s constraint, a fixed-size channel array or contract (it would cap FkChain's length, and the matrices would allocate anyway).
- **Phase 4 settled:** the internal `settings` plug is `ModulePlugInfo::followsPlug` (pass 2 reads the followed plug's `parentStructure` entry), `createModule` runs the modifier twice to add and wire the channels (as `createConstraint` does), and the FK chain is solved at every blend so each control's offset stays current. Details in `two-bone-ik.md` section 8.
- **Phase 7 settled:** `ModuleDescriptor::spaceDelta` is a free function pointer like `inverse`, `(module, slot, label) -> delta`, and `TwoBoneIkNode::spaceDelta` reads the same two deltas `evaluate` gives the pole from the module's plugs (the child plug's parent motion, and the `ik` socket against its rest), so the command runs no solve. D27's formula has one home, `RigPoseScene::matchControlToNewDelta`, now built on `fitLocalToChannels` (the constraint's switch calls it too): a locked or driven channel warns only when its kept value differs from the match's, where it used to warn for every locked channel. A new `ControlSpaceScene` finds a control's space of either kind, so the two commands stay thin. `D_old` is the control's current enum value, not a stored one. `ControlSpace.module` is appended with a default in Python, so a caller that builds the dataclass by position keeps working.
- **Consequence:** one module node (`twoBoneIkModule`, `0x00218F`), six channel names, two commands (`setRigIkFkBlend`, `setRigControlSpace`), a `module` key on `getRigControlSpace`, `ModulePlugInfo::allowsConstraint`, a descriptor hook, and a mayadev rig panel edit. Built in eight phases, one commit each, with a `bench` run on the perf rig (D36).

### D53. Module source files and classes end in `Module`: `FkChainModule`

**Status:** Decided (author, 2026-11-15).

Layout, Aim and TwoBoneIk already had `<Name>Module.h/.cpp` and `<Name>ModuleNode`; FkChain alone was `FkChain.h/.cpp` and `FkChainNode`. It is now `FkChainModule.h/.cpp` and `FkChainModuleNode`, and every future module file follows the pattern.

- **Not renamed:** the template `moduleType` (`FkChain`, `Aim`, ...) and the node type name (`fkChainModule`). Both are public: saved templates and rigs depend on them, and none of them carries the suffix in `moduleType`.

- **Impact:** none on saved rigs, poses, animation or templates. Only C++ names and paths changed.

### D56. Ribbon module: a virtual ribbon with ik controls, tweakers and stateless twist
**Status:** Leaning (author, 2026-11-17, three rounds of answers). Built in part on 2026-11-17: phases 1, 2, 3 and 5 and the docs (the math, the node, the layers, the inverse). Not built: `fkStyle` and the perf rig with `bench`. Design: `ribbon.md`, with an "As built" section. Branch `ribbon-module-planning`.

A virtual (no curve, no mesh) parameterized ribbon for tails, spines and limb segments: n bind joints already distributed, j control joints (start, end, interior ones that ride the curve), a twist that runs the whole chain and one sine layer held on the first control, scale with a three-point volume profile, and an inverse in v1.
- **Why:** the handoff sketch's driver placement through `offsetParentMatrix` was a module output feeding its own controls (D17, D52), and its accumulated twist state made output depend on frame order (D36). Reading each interior control's local matrix removes the cycle without a node pair, and the branch-picking twist, `secondary + wrap(extracted - secondary)`, reaches past 180 degrees with no state and no keyed twist channel.
- **Decided:** a control layer stack (optional FK, IK, hidden tweakers as the bind joints' parents), `fkStyle` as a template key, start and end driven by another module's sockets or self-contained (an arm is two ribbons), `uniformSpacing` dropped (rest spacing kept), rest up vector from the start joint's rest axis, `volumePreserve` with start, mid and end weights, inverse in v1 with the tweakers as the exact residual.
- **Round three (2026-11-17):** reference space is the first child plug's parent, channels live on the first IK control, FK controls are a real chain read through their local matrices, v1 layers are twist, bow and one sine behind a per-layer function, `lambda` clamped for the volume exponent only, driven start and end visible and with no space match. See `ribbon.md` section 9.
- **Built (2026-11-17):** `core/RibbonMath` (the solve, no Maya types), `maya/modules/RibbonModule` (`ribbonModule`, MTypeId 0x002191, moduleType `Ribbon`), the channels on the first control (15 after the revision below), ik controls plus hidden tweakers, a `start` and an `end` child plug, an inverse that is exact for every bind joint present, and the suite (the contract, 12 hand-worked pose cases, behaviour, plan checks and a golden snapshot).
- **Differences from the draft** (all in `ribbon.md` "As built"): the module layer already fed every control's local matrix to its module, so no new plug type was needed. A bind joint's parameter is its share of the control polyline's rest length, not an arc-length table. An interior control's own roll twists the ribbon too. `volumePreserve` defaults to 0. The ribbon is solved in the rest world and carried by the `start` plug's parent motion, which is the draft's "parent of the first child plug" without inverting anything per control.
- **Revision (author, 2026-11-17, phase 2):** (1) **The ends' twist runs the whole chain.** The two ends' total twists (the branch-picked angles) ramp linearly in `u` along the ribbon, and every interior control's offset parent matrix carries that ramp about the base curve's tangent, so a roll on the start reaches the far end and not only the next control. An interior control's own roll adds on top of the ramp at its place (its total is ramp plus own), and the joints between controls follow the controls' totals linearly. A consequence animators will see: an interior control's local axes are rolled by the ramp, so its translate channels move it along the rolled axes. (2) **`twistFalloffPower` removed**: the roll between controls is linear, which the ramp makes the only sensible spread. (3) **`bow` removed**: the sine layer is the only nonlinear displacement left. `bendRoundness` stays: it sizes the end tangents and is not a layer. The channel count is 15, and the `RibbonChannel` order closed up (nothing was committed, so no saved pose, animation or golden depended on the old order). Rejected: keeping `twistFalloffPower` as a shaping curve over the ramp (a second way to spread twist, with no case that needed it).
- **Scale** (checked 2026-11-17): control scales interpolate by smoothstep between controls, and `volumePreserve` multiplies the Y and Z axes by `lambda^(-0.5 * volumePreserve * w(u))`. Hand-worked pose cases cover a stretch (lambda 1.5), a squash (lambda 0.5), half preservation, the profile weights, a control's own scale on its own, and a control's scale together with volume (they multiply).
- **Measured (2026-11-17, `bench` parallel, headless):** the first build measured the 50-rig ribbon rig at 308 ms against a 72 ms floor (ratio 4.3). **That number was a bug, not the ribbons' cost:** `compute()` read its stored rest arrays with `jumpToElement` and failed on a reopened scene, because a saved scene drops array elements that equal their default (knot 0, an identity offset) and an array with none has no handle. Every ribbon failed its compute every frame and printed an error. `compute()` now reads a missing element as its default (test: `test_a_saved_and_reopened_scene_evaluates_the_same`). **After the fix: 50 rigs 107 to 116 ms/frame (8.6 to 9.4 fps) against a floor of 66 ms (15 fps): ratio 1.6 to 1.7. 20 rigs 47 to 50 ms (20 to 21 fps).** The rig was 93 ms against 57 before the ribbons (1.6 to 1.7, D52), so the ribbons add no measurable ratio. Both are over D36's 1.5 and 30 fps targets, for the reason D36 gives (the `rigControlNode` premium over a native transform), and the ribbon is not the cause. Probes: `RibbonMath::evaluate` for 3 controls and 12 bind joints costs 5.5 microseconds, so 350 ribbons are about 2 ms of a frame, and the handoff's suspects (struct initialisation, plug copies, three curve evaluations per bind frame, `pow`/`sin`/`cos`, the matrix inverse) are not worth changing. Hidden tweakers cost nothing extra headless: 3000 controls un-hidden gave 111 to 112 ms against 113 to 122 for the same scene hidden (noise is about 5 ms).
- **Amendment (2026-11-17, phase 1 of `ribbon-twist-follow.md`):** the end's total twist also includes the twist of its plug's motion relative to the start plug's (`RibbonMath::Input::endDelta`, the swing-twist split about the end's rest X), so an end parent that twists (an elbow, a chest) twists the ribbon, and an arm's two ribbons meet at the elbow with the shoulder's twist easing in. Before it, the end plug's roll was ignored: the probe measured a seam pop equal to the shoulder's twist (60 and 170 degrees), and a start parented to the shoulder gave no ease. A Twist constraint type was rejected: a plug delta carries the whole ribbon rigidly, about the rest axis. No name changes, so poses and animation are unaffected. A rig with a twisting end parent looks different; no rigs need to survive. **Correction (2026-11-17, found on the solomon asset):** the first build of this term read the twist of the plug motion about the world X. The plug deltas are motions in world axes, so the module now conjugates the end's motion by the end control's rest rotation and reads the twist about the control's own X, the bone's axis (commit `ea4b0d3` on main had the world-X version, right only for a bone along X). `test_a_tilted_arm_follows_its_end_plugs_twist_about_the_bone` covers it. Phase 2 adds optional `startAimBlend` and `endAimBlend` `moduleArgs` keys (0 to 1, default 0): the same-named channels' default, so their rest (D34), because a template had no way to build a shoulder or thigh aimed. Rejected: changing the channels' own default to 1 (it would move every Ribbon's rest, tails included) and leaving it to the animator (lost on a zero or a pose load). The two keys are public API.
- **Open:** `fkStyle` (not built), a GUI look at the control shapes, and a read-phase warning for control joints whose X points away down the chain.
- **Consequence:** the channel names (`startTwist`, `endTwist`, `sineAmplitude`, `sineFrequency`, `sinePhase`, `sineOrient`, `sineStartFalloff`, `sineEndFalloff`, `startAimBlend`, `endAimBlend`, `bendRoundness`, `volumePreserve`, `scaleStart`, `scaleMid`, `scaleEnd`), the `controls` and `joints` moduleArgs keys, and the child plug and socket names are public API now. `ModuleInverseContext` gained `ikControlCount`, which `RigInverse` fills from a module's `ikControlCount` attribute.

### D57. Control placement is derived from the bind joints, with no control joints in the skeleton
**Status:** Decided (author, 2026-11-17). Phases 0 to 5 built (the -X chain, `core/ControlPlacement`, the Ribbon, TwoBoneIk, the perf scenes, the docs pass and the mayadev report). Design and build phases: `derived-controls.md`.

The Ribbon places its ik controls evenly along its bind joints (`controlCount`, default 3), and TwoBoneIk derives its IK handle, pole and settings from its three joints, so neither needs control joints in the skeleton. Orientation comes from the bind joints, and a joint whose axis is off the chain is a read-phase error. A chain whose -X points down is accepted (mirrored limbs). Control names are a base plus `IK`, `Tweak` or `FK` (`spineIK_00`, `armIK`), the base set by an optional `controlName`. The pole and settings take optional world-space `poleOffset` and `settingsOffset` vectors (the settings default is a quarter of the limb's length along world +Y, and a straight limb puts the pole out along the root joint's -Y rather than failing). Ribbon placement follows a smooth spline through the bind joints, with the control cap at 8. The foot pivots (`heel`, `bankIn`, `bankOut`) stay marker joints.
- **Why:** 35 of the 95 joints in a real skeleton were `skin: false`, all exported, and 20 of them carried no information beyond the bind joints. Each one also changed the skeleton hash. **Rejected:** a locator input type with a `markers` array in `skeleton.json` (a new node type, new tools, a hash decision to reopen), and keeping marker joints with `export: false` (fixes only the engine side).
- **Reverses:** D52 decision 1 (marker joints for `ik`, `pole` and `settings`, and its rejected computed pole) and D56's `controls` selectors in `moduleArgs`. D54's hash rule stands.
- **Built, phase 2 (2026-11-18):** the Ribbon's `moduleArgs` are `joints`, `controlCount` and `controlName`, `moduleVersion` 2 turns an old `controls` list into `controlCount`, and the ik controls have no joint (`wireJoint` is skipped for them). Usages are `<base>IK_<nn>` and `<base>Tweak_<nn>`. A tweaker's usage is no longer its bind joint's, though its node is still named from the joint. The inverse takes the end controls from the first and last bind joints and leaves interior controls at their sidecar or rest values, the tweakers carrying the difference. A usage two modules share is the existing D25 error.
- **Built, phase 3 (2026-11-18):** TwoBoneIk's `moduleArgs` are `joints`, `controlName`, `poleOffset` and `settingsOffset`. `moduleVersion` 2 drops `ik`, `pole` and `settings`, and cannot turn the old marker positions into offsets (the update step has no scene), so an old template builds with the derived places and its pole and settings controls move (author, 2026-11-18: accepted). The handle sits at the end joint with its rotation. The pole and settings controls take **world axes**: their rotation is locked, so their orientation only sets how their translate channels read, and world axes are the least surprising. The offsets are world vectors with X negated on a mirrored copy, through `isMirror()` in `planFromJson`. A straight limb (mid within 0.1 percent of the limb's length of the root-to-end line) puts the pole out along the root joint's -Y (author, 2026-11-18: -Y is right, not -Z). A straight limb that runs along that same axis puts the default pole on the root-to-end line, so the read phase rejects it and asks for a `poleOffset`: a pole on that line has no bend plane. Usages are `<base>IK`, `<base>Pole` and `<base>Settings`, the base being `controlName`, else the first joint's usage without a trailing `_NN`. The IK, pole and settings slots have no joint (`wireJoint` is skipped, no `jointOPM` element). The inverse is unchanged: it never read the marker joints. `MathUtils::toMat4` and `toMMatrix` moved to the shared layer from the Ribbon.
- **Built, phase 4 (2026-11-18):** the perf generator writes `moduleVersion` 2 with `controlName`, `controlCount`, `poleOffset` and `settingsOffset` and no limb marker or ribbon control joints (296 joints, was 354; Aim keeps its markers). `derived_controls()` lists the 58 controls with no joint, and the floor scene builds them as native transforms, so both scenes keep 348 controls. `bench` (parallel, once): `complex_x20` 23.0 fps (was 21.8), `complex_x50` 9.3 fps against the floor's 16.1, a ratio of 1.74 (was 1.72). Both are still below D36's target (30 fps for 20 rigs, 1.5 times the floor on 50), as before: removing the joints did not change the cost.
- **Built, phase 5 (2026-11-18):** a docs verification pass only, no code. `docs/modules.md`, `controls.md`, `templates.md`, `skeletons.md`, `architecture.md`, `commands.md` and `README.md` already described the derived controls (marker joints remain only for Aim's `target` and `up`, and the foot pivots), with no stale `ik`, `pole`, `settings` or `controls` keys in a current example. `CLAUDE.md` now says the Ribbon's controls are derived. The three open questions in `derived-controls.md` section 9 are closed. mayadev call sites were searched and reported to the author, not edited. No suite rerun (no test or fixture changed).
- **Amended 2026-11-18 (author):** the settings control's default offset is a quarter of the limb's length along world +X, not +Y. On the mirrored side it is -X (`placeLimb` takes `mirrored`, passed from `planFromJson`), so the two sides reflect. An explicit `settingsOffset` is unchanged. Saved poses are unaffected (the controls' rest places move, their channel names do not).
- **Consequence:** the `controls` key leaves Ribbon's `moduleArgs` and `ik`, `pole` and `settings` leave TwoBoneIk's (both `moduleVersion` steps). Control usages change, so saved poses and animation for them stop matching. Open questions are in `derived-controls.md` section 9.

### D59. TwoBoneIk and Ribbon template keys for defaults, orientation and an FK layer
**Status:** Built (author, 2026-11-18). Built in steps on branch `claude/ribbon-two-bone-ik-updates-d3291d`, one commit each.
- **Step 1, built:** TwoBoneIk takes `ikFkBlend` (0 to 1, default 1) in `moduleArgs`. It is the built value and the rest value of the settings control's `ikFkBlend` channel, so an arm builds in FK and `zeroRigControls` returns to FK. Additive, so no `moduleVersion` step. Rejected: a separate `defaultMode` string, since the channel is already the blend.
- **Step 2, built:** `ikOrientToWorld` (the IK handle's rest frame is world-aligned) and `ikAlignToPole` (a yaw about world Y so +Z points at the pole's horizontal direction, for feet). Two flags because an arm's pole sits behind the elbow, so one flag would turn an arm's handle 180 degrees. `ikAlignToPole` without `ikOrientToWorld` is an error, not a silent no-op, and so is a pole straight above or below the end joint. The math is `ControlPlacement::placeWorldIkHandle` in `core/`. The joints' rest offsets (`computeRest`) absorb the handle's rotation, so the bind pose is unchanged. Mirror: the yaw follows the reflected pole. A world-aligned right handle has the left's axes, so its translate channels read differently from a joint-aligned one; the channels' `mirrorCopy` or `mirrorNegate` modes are unchanged.
- **Step 3, built:** Ribbon `fkStyle` (D56 phase 4) with `fkControlCount`, defaulting to `controlCount`. The chain has its own size, so the D56 line "each IK control takes its frame from the FK control at the same index" became "from the fk base curve at the ik control's own parameter", with the rest offset measured there (see `ribbon.md` section 3.1). The fk controls are the last slots after the tweakers, with no joint and no socket. With an fk chain the ribbon has no `end` child plug: the whole ribbon follows `start` and the end rides the chain. Rejected: keeping the `end` plug and letting it twist the ribbon as before, since the fk chain's end already is the end's motion and two drivers of one end is the kind of surprise animators hit. No new perf-rig instances, since this extends an existing module. `bench` (2026-11-18, one run each, parallel): complex x20 16.5 fps (60.6 ms), the same scene with every ribbon given an fk chain (`complex --fk-style`) 16.1 fps (61.9 ms), so the chain costs about 1.3 ms for 20 rigs, within run-to-run noise. Complex x50 147.7 ms against the floor's 91.1 ms is 1.62 times. Both are below the D36 targets (30 fps for 20 rigs, 1.5 times the floor), and there is no baseline run from before D59 in this session, so whether steps 1 and 2 moved them is not measured (D56 recorded 20 to 21 fps and 107 to 116 ms against a 66 ms floor on an earlier run).

### D62. Limb: one module that runs the TwoBoneIk and Ribbon solves with one continuous ribbon

**Status:** Decided (author, 2026-11-19: one round of answers). Built through phase 3. Design, interface and phases: `limb.md`.

An arm or leg built from `TwoBoneIk`, two or three `Ribbon` modules and `Swing` and `Twist` constraints has a crease at the elbow, 21 controls, five nodes and the ribbon channels repeated on two controls (checked on the solomon rig). `Limb` is one module with one spline through start, mid and end.

- **Inputs:** three IK/FK joints and 5 or more bind joints (they may have child joints: inheritsTransform is off, so a child is not dragged; author, 2026-11-22), with exactly one at the mid joint and none stacked. `controlCount` ribbon ik controls, default 5, minimum 3. No fk ribbon.
- **Channels:** every module-wide channel (`ikFkBlend`, `stretch`, `soft` and the ribbon's) is on the settings control, under the names already in use. `startAimBlend` and `endAimBlend` are dropped. `roll` and `pin` stay on the handle and the pole.
- **Evaluation:** the IK/FK solve, then the ribbon's end frames from the blended joints (start: translation and swing of the start joint, as `Swing`; end: translation and twist of the end joint on the swing of the mid, as `Twist`), then the ribbon solve. No constraint nodes.
- **DAG parenting (author):** the ribbon ik controls are leaf children of the start plug's DAG parent, and the tweakers are leaf children of the first ik control.
- **Reuse, and the coupling:** `Limb` is not a subclass of `TwoBoneIk` or `Ribbon`. It calls their solves, which phase 0 moves into shared functions with no behaviour change, and their channel specs, control derivation and inverses. **A change to those, or to `core/RibbonMath` or `core/SwingTwist`, changes `Limb`.** The warning is in `limb.md`, `two-bone-ik.md`, `ribbon.md`, `CLAUDE.md` and three headers, and `test_limb_matches_parts` checks that the three agree.
- **Hand and foot:** one `Limb`, not `Arm` and `Leg`. An optional `ikTarget` child plug sets where the end joint reaches, defaulting to the handle's own world. A later `ReverseFoot` module hangs from the `ik` socket and feeds `ikTarget`, so the foot pushes up the ankle target while the handle stays the foot's root. It makes a module-level loop that is acyclic at plug level, so the cycle check in D17 gets a declared exemption for that plug (author-approved). Rejected: a foot inside `Limb`, and a combined `Limb` and `ReverseFoot`. How an IK match works with a raised foot is left to the `ReverseFoot` design.
- **Names:** type `Limb`, node `limbModule`, MTypeId `0x002192`, controls `<base>FK`, `<base>IK`, `<base>Pole`, `<base>Settings`, `<base>RibbonIK_<nn>`, `<base>Tweak_<nn>`.
- **Migration:** none. No legacy rig has to survive (author), and the solomon template moves to `Limb` by hand in phase 6.
- **Phase 1, built (2026-11-19):** the curve through the mid joint is D59's fk base curve with the limb's three blended joint frames as the chain (`RibbonMath::buildAnchoredSetup`, `Setup::fkAnchors`, `Input::fkWorld`), so there is no new curve type. Two changes beyond the anchors: the anchors' roll about the curve also twists the bind joints, and the ik controls are placed on the anchor curve from chosen parameters (the mid one at the mid joint's), which amends D57 for `Limb`. The elbow is rounded, not creased, and no rounder than the Catmull-Rom tangent at the mid knot gives (46 and 34 degrees in the two steps at a 98 degree bend with four bind joints a side). A mid-handle scale is the open choice (`limb.md` section 5.1). Verified by a standalone probe over hand-worked cases (34 checks) that become `Limb` pose cases. The old `Ribbon` is unchanged.
- **Phase 2, built (2026-11-19):** the `Limb` module (`limbModule`, `0x002192`). The two-bone half is shared as `TwoBoneIkPart<Node>` (attributes, plug reads, slots, channels) and `TwoBoneIkSolve::planSlots`, and the ribbon's channels, stored rest and evaluation as `RibbonSolve`, so `TwoBoneIk` and `Ribbon` now run on the code `Limb` uses. **Amended by the author (2026-11-19): the elbow is a sharp corner by default.** `bendSoftness` (0 to 1, rest 0, on the settings control) blends from the polyline through the joints to the smooth curve, in both the base curve and the detail curve, and replaces `bendRoundness` (which, with the aim blends, is not a Limb channel). A curve degree was rejected: a cubic with chord tangents is exactly a line, so one channel spans both. ### D71. FkHierarchy: a separate module that builds an FK control for every joint under one root
**Status:** Decided (signed off by the author 2026-11-23) and built the same day on branch `fk-hierarchy`. Design, and where the build differs from it (section 16): `design/fk-hierarchy.md`.

A new module, `FkHierarchy`, takes a `root` selector and an optional `terminators` list, and builds one FK control for the root and for every joint below it, down to each terminator (included) or to every leaf when there are none. One child plug, `start` (the root). Sockets are named from joint markup: the side lowercased, then the usage (`left_spine_00`), with `start` also naming the root's. FkChain is unchanged.

- **Why a new module, not an FkChain extension:** FkChain's interface is positional (an ordered `joints` list, `index_<n>` sockets, `start` and `end` aliases), its names are public API, and its compute is a straight loop on the most-used module. A tree changes all three. The two share control creation, wiring, `solveControlStep` and the inverse step. Rejected: a mode on FkChain, which puts two interface shapes behind one `moduleType`.
- **Compute stays one linear pass:** controls are stored in pre-order, a `controlParentIndex` int array gives each control's parent, and a delta is kept only for a control that has children. Splitting the tree into chains was rejected (the same cross-chain lookup with more bookkeeping). A separate `solveFkHierarchy` rather than a flag on `solveFkChain`, so FkChain's loop, goldens and D36 numbers cannot move.
- **Author's rules (2026-11-23):** one root per module (a second root is a second module); every joint and control has unique markup (D25); a joint added under the root builds and its control inherits its parent; the joints are found with `MItDag`; it mirrors (D28), and a mirrored terminator that matches no joint on the other side is dropped with a warning, while a mirror that needs specific terminators is written out as its own module.
- **Also decided (2026-11-23):** a joint under the root that another module claims is a template error, avoided with a terminator, and there is no `exclude` list (a second `FkHierarchy` below it covers that); the side is lowercased and the usage keeps its case; `start` is the root's alias and there is no `end`; controls are in depth-first `MItDag` order, not sorted; the ordering rule is in `core/` and the walk in the Maya layer. 
- **Built (2026-11-23):** `core/HierarchyPlan`, `FkHierarchyModule`, the inverse with `ModuleInverseContext::parentIndex`, and a mirror rule the draft missed: `TemplateMirror` swaps a leading `left_` or `right_` on a socket name, so a mirrored module on a markup-named socket points at the other side's. Suite on that build: TOTAL 1562 passed, 15 skipped.
- **Perf rig and `bench` (once, at creation, D36):** the complex rig gained 4 `hierarchy_specs` (6 modules built, 8 joints each): 408 joints, 524 controls, 103 constraints. `bench` parallel, one session: 20 rigs 13.8 fps (72.7 ms); 50 rigs 5.5 fps (181.8 ms) against a native floor of 8.9 fps (112.7 ms), a ratio of 1.61. **Both are below D36's target** (30 fps for 20 rigs, 1.5 times the floor on 50). The Limb entry's last run (360 joints, 476 controls) was 15.7 to 16.4 fps and a ratio of 1.74, so the 48 joints and controls added here are within the run-to-run drift. The cost is still node and control count, as in D52.
- **Consequence:** a new module name and node type (`fkHierarchyModule`, MTypeId `0x002193`), one attribute, one optional field on the inverse context, and the gate steps: perf rig instances and one `bench` run when it is built.

### D74. ReverseFoot: a foot module on a Limb, with roll, pivot and toe channels, an FK toe, a blend driven by the limb, and an inverse that solves three channels
**Status:** Decided (author's answers recorded, the seven open questions answered and signed off, 2026-11-24; `reverse-foot.md`). Phases 2 to 4 built 2026-11-24: `core/FootSolve`, the module (control, channels, plugs, the `ankle` socket), the toe and toe tip, the toe FK control and `ikFkDriver`. Phase 5, the inverse and the match, built 2026-11-25 (the entry below). The perf rig with its one `bench` run (phase 6) is not. Needs D73. Design, interface, solve, inverse and phases: `reverse-foot.md`.
A separate module that hangs from a Limb (D62) by two child plugs: `ik` (the IK half, from the Limb's `ik` socket, outputs the `ankle` socket that feeds `ikTarget`) and `ankle` (from the Limb's `end` socket, the ankle as it is, for the toe and toe tip). Inputs are `joints` (ankle, toe, toe tip) and `ikFkDriver` (the Limb or TwoBoneIk whose `ikFkBlend` drives the foot through a locked input). The pivots are six markers found by role on the foot's side, in a fixed order (the 2026-11-24 bullet below: `reverseHierarchy` was removed). Channels only, on one channel control (`<base>Foot`, derived from the `ball` marker and aligned to the world, author 2026-11-24; the IK leg control would need a cross-module channel): `footRoll` (peel, split in the node at `breakAngle`, no set-driven keys), the raises and swivels of each pivot, `ballRoll`, one signed `bank` (positive toward world +X, so "out" on a left foot and "in" on a right foot, `mirrorNegate`) and `toeTap`. The only new FK control is the toe's: the ankle comes from the Limb's IK or FK end. The foot drives the toe and toe tip, never the ankle, which the Limb owns. `reverseHierarchy` has no ankle entry.
- **No cycle:** two stages in separate attribute groups (D62 phase 4: Maya orders by attribute). Stage 1 reads `ik`, stage 2 reads `end`, and the cycle check gets one more blind-socket rule.
- **Inverse:** the handle absorbs the rigid foot offset, so the ankle and toe come back exactly for any channels. Joint-solved: `footRoll` (the ankle's total pitch), `bank` (its roll) and `toeTap`. Not solvable: the raises, swivels and `ballRoll`, which come from the sidecar or the rig. `RigInverse` gets a pre-pass that solves the foot first and gives the Limb the offset (`ModuleInverseContext::ikTargetOffset`), so the match through `setRigIkFkBlend` does not pop. This closes the open item in D62. (As built in phase 5 the offset is `ModuleInverseInput::ikTargetMotion`, not a context field: see the phase 5 entry.)
- **Phase 5 built (2026-11-25): the inverse and the match.** The API (signed off by the author, 2026-11-25): `ModuleInverseContext::moduleRest` (a module's own stored rests, read once per solve by the new `ModuleDescriptor::readInverseRest`: the foot's ankle, ankle plug, toe and toe tip rests and its six pivots), `ModuleInverseInput::ikTargetJointWorld` (for the feeding module: the Limb's end joint from the source) and `ikTargetMotion` (for the Limb: the foot's motion `F`), `ModuleInverseResult::channels` (scalar channels a module derived from the joints, written by the driver) and `ikTargetMotion` (what the foot hands the Limb), plus `ModuleInverseInput::ikHandleParentDelta` (below).
  - **The math.** `ankle = ankleRest * F * H`, with `F` the foot's motion from its channels at rest pivots and `H` the handle's motion since rest. The Limb's handle goes at `ikRest * F^-1 * ikRest^-1 * reach`, so the forward reach (`ikRest * F * H`) lands on the joints. `toeTap` is the pitch left in the toe once the pivots before it and `H` are taken out (`FootSolve::solveToeTap`), and the toe FK control comes from the toe joint exactly.
  - **The gauge: "subtract the sidecar" (author, 2026-11-25).** `footRoll` and `bank` take the pitch and roll that the given channels (the sidecar's, else the rig's) miss, added to their given values (`FootSolve::solveAnkleChannels`); every other channel is kept as given. So a sidecar's raise is not counted again in `footRoll`, and given channels that already make the turn come back unchanged. Rejected: every pitch into `footRoll` whatever the sidecar says (a sidecar with a `ballRaise` would then double it).
  - **Read in the handle's space (author, 2026-11-25).** The pitch and roll are read after taking out the motion of the space the Limb's handle hangs in (`ikHandleParentDelta`, the Limb's ik child plug's parent: a Layout's), so a turned, tilted or scaled Layout stays in the Layout and gives back the foot's own channels. Rejected: world space, where a tilted Layout's pitch and roll went into `footRoll` and `bank` and left the toe up to 0.0025 off. The handle's own pitch and roll still go into `footRoll` and `bank` (the handle takes the heading and the position, `reverse-foot.md` section 10), so a turned handle comes back with different channels, and the toe is exact only when the channels can make the pose.
  - **The pre-pass runs per Limb, inside the sweep, just before the Limb** (not before the sweep, as first written): the Limb's parents are solved by then, so the handle's space is known. The foot runs again in its own place after the Limb, with the same input, and gives the same answer. A Limb's `ikTarget` source is found from the `ikTargetMatrix` connection. A rig with no foot keeps its order and results.
  - **The handle carries its space's scale.** The handle has no scale channel, so in the scene it takes the Layout's scale; the inverse now gives the reach that scale, so the handle's local comes out rigid. Without a foot only the reach's position is read, so nothing changed there; with one, `F` turns about pivots away from the handle and the unscaled handle moved the reach.
  - **The match.** `TwoBoneIkPart::computeMatch` takes the target's motion when it is connected, solves the joints as the Limb's compute does, and gives the inverse `F` as the target's motion over the handle's, so `setRigIkFkBlend` from FK to IK with a raised foot puts no pop in the ankle and keeps the foot's channels. The match outputs are affected by the ikTarget inputs (they feed nothing, so no loop).
  - **The toe is matched both ways (author, 2026-11-25).** The author found the toe popped on IK to FK through the active rig panel. The foot gained match outputs of its own, pulled only by the command: `fkMatchLocal` at the toe FK slot (`localFromWorld` on the toe as it is), `ikMatchToeTap` (`solveToeTap` with the channels kept and the handle the Limb's match places, `H = F^-1` times the ankle's motion) and `matchWarnings` (the IK side's: a toe turned off the pitch `toeTap` holds). `setRigIkFkBlend` finds the feet through `RigTraversal::getBlendFollowers` (the modules whose `ikFkBlend` the build connected from the Limb's) and writes both sides with the Limb's, in one undo step, and shows a foot's warnings only for a switch toward IK. `computeToe` and the match share `solveToe`. Rejected: a second command for the foot (two switches for one limb, D59 step 3), and solving the toe in the command, which would put `FootSolve` and the pivots outside the node.
  - **`decomposeRotation` divides out a uniform scale**, for a rig scaled through its Layout.
  - **Tests.** `ReverseFootInverse` (no sidecar, the sidecar gauge, a tilted and scaled Layout, the match with a raised foot), the contract round trips with test_limb's rules for its Limb (`LimbRoundTripRules`: the ribbon's ik controls not posed, since their scale with `volumePreserve` shears the bind joints beyond the tweakers) and the foot's handle moved but not turned, `test_limb_matches_parts_with_a_foot`, and the core gauge tests in `FootSolveTests.cpp`.
- **Rejected:** `Leg` and `Arm` modules, and a foot inside `Limb` (D62, and the author 2026-11-24: no `Leg`). FK pivot controls as a second interface (two drivers of one state, D59 step 3). The foot owning an `ikFkBlend` of its own. One plug on `ik` only (the foot would not follow the FK ankle).
- **The Limb must take the foot's ankle (2026-11-24).** A Limb whose `parentStructure` had no `"ikTarget": "foot_00_L_MOD.ankle"` built with no error and the foot moved nothing (the author's solomon test). `ModuleInterface` gained `driverPlug` and `driverPlugSocket`, the driver's plug a follower must feed and from which of its sockets, and `validateBlendDrivers` makes a missing or different entry an error that names the line to add. Data on the interface rather than a foot branch in the validator. Rejected: wiring `ikTarget` implicitly from `ikFkDriver` (a connection the template does not show). A TwoBoneIk has no `ikTarget`, so it can no longer be a foot's driver (it never moved the ankle).
- **`reverseHierarchy` removed; the roles and the chain order are the module's (author, 2026-11-24).** The foot finds its six pivot markers by markup on its own side (`[Left, heel]`, `[Left, ball]`, `[Left, bankOut]`, `[Left, bankIn]`, `[Left, toeTip]`, `[Left, toe]`), all required, and chains them in the fixed order heel, toeTip, bankOut, bankIn, toe, ball (`FootSolve::chainOrder`). Why: every foot has all six and none is worth leaving out, so the list never differed; and the order is rig behaviour, not data. The author's solomon order (heel, ball, banks, toeTip, toe) put the toe under the ball, so a roll of 20 tipped the toe 20 degrees and its tip 2.9 into the ground. In the fixed order the toe stays planted below the break and the toe tip stays on the ground past it, which is also the "fixed ground pivots" result D74's phase 2 entry records as the rejected alternative (ankle y 20.14, z 6.33 at a roll of 50): the literal hierarchy is kept, and the fixed order gives that result. Removed with it: `findRole`, `allowedRoles`, `checkRoles`, the "missing role removes its channels" rule (all 11 channels always exist), and four validation cases. The pivot sockets list in chain order (`heel`, `toeTipPivot`, `bankOut`, `bankIn`, `toePivot`, `ball`): names unchanged. Consequences: (1) the ball turns the ankle before the bank, so a ball roll with a bank no longer reads back as exactly `footRoll` and `bank` in the roll-first decomposition (the handle absorbs the rest, the joints come back exactly; a heel roll with a bank still does); phase 5 picks its gauge with this in mind. (2) The IK toe stays at its pivot and is pulled to bone length from the ankle, so a `ball` marker away from the toe joint slides the toe slightly as the ankle rises; the docs say to put the ball marker at the toe joint. Not built: two feet on one side (a marker prefix argument would add it compatibly); the author expects a quadruped leg to be a module of its own.
- **The ball pivot is removed; the toe pivot is the ball of the foot (author, 2026-11-25).** The roll below the break (`peel.ball`), `ballRaise`, `ballSwivel` and `ballRoll` turn about the `toe` marker, and the `ball` marker and role are gone: five pivots, chained heel, toeTip, bankOut, bankIn, toe. Why: the axes come from the derived foot frame, never a marker, so a ball pivot apart from the toe could only move the roll's centre off the toe joint. There the ankle-to-toe distance changed as the heel lifted, the length-keeping pull in `computeToe` slid the toe along the line from the ankle, and the toe tip, which rides the toe rigidly, dropped (seen on the author's asset). The alternative kept the ball pivot and made a ball marker off the toe joint a build warning or error: two markers that must always coincide is a special case with no use. **`ballSwivel` carries the toe bone (author, same day):** the swivel turns the whole foot about the ball, toe tip included ("squash a bug"), while the roll below the break, `ballRaise` and `ballRoll` turn the ankle only, so the toe stays planted for them. Inside the toe pivot the swivel is already the outermost turn, so this is a hierarchy level at the toe marker's position (`toeMotion` = `toeTap`, then `ballSwivel`, then the pivots before the toe; `solveToeTap` undoes the same), not a reason to bring the ball marker back: a separate marker would only matter if the swivel's centre had to differ from the roll's. Before this the toe bone took no turn of its own pivot, so a ball swivel swung only the heel. **Public API:** the channel names are unchanged (`ballRaise`, `ballSwivel`, `ballRoll` name the ball of the foot; `toeRaise` and `toeSwivel` stay the toe tip's). The `ball` socket is removed, and the other pivot sockets keep their names and indices. The foot control now sits at the `toe` marker. `Role` values are stored on the node, so they are explicit and `Ball`'s value 1 is retired. A `ball` marker left in a markers file is not read. The alternative, taking the roll axis from the ball marker's X and the bank axis from the bank markers' Z, would follow a slanted ball line but makes the pitches non-parallel, so the inverse could no longer add them into `footRoll`. Because the Axis locators show a marker's rotation, a pivot marker that is not world aligned (within 1e-3 per matrix element) is a build warning, one per foot, naming the markers.
- **Phase 2 built (2026-11-24): `core/FootSolve`, and how the chain composes (author's answer).** The design's `pivot_i = pivot_{i-1} * rotation_i * restOffset_i` is the **literal hierarchy with the heel as root**: a pivot is carried by the pivots before it. Because a pivot's own turn about its own position does not move it, that is the same as `ankle' = Rot_0(Rot_1(... Rot_n(ankle)))`, each about a REST pivot and a rest axis of the foot frame, the last pivot (the toe tip) moving the ankle first. The author was shown the alternative (every rotation about fixed ground pivots, applied in list order) and chose the hierarchy knowing what it does past the break angle: with heel z -10, ball z 10, toe tip z 18 and the ankle at (y 8, z -6), a roll of 50 over a break of 30 puts the ankle at (y 19.53, z 7.63) and carries the toe tip 4 below the ground (the alternative gave y 20.14, z 6.33 with the tip on the ground). Signs, all positive about the axis (right-handed): a ball or toe tip pitch is about lateral (heel up), a heel pivot's angle is minus that (toes up), swivels are about up (toes toward lateral), `ballRoll` and `bank` are minus a turn about forward, and the bank turns about the pivot on the +lateral side for a positive value. Within one pivot the roll turns first, then the pitch, then the swivel, the order `decomposeRotation` reads back. Where a roll sits between two pitches (bank between the ball and the toe tip, past the break), the pitch and roll the inverse reads are not the forward `footRoll` and `bank`: the handle absorbs the difference, so the ankle and toe still come back exactly.
- **Phase 4 built (2026-11-24): stage 2, the toe FK control, `ikFkDriver`.** (1) The foot drives the toe and toe tip and has the toe FK control `<toe usage>FK`, with FK before a trailing `_NN` (`ball_00` gives `ballFK_00`; fixed 2026-11-24, it gave `ball_00FK`, which failed validation) (rotate only, control slot 1, the foot control slot 0, joints slots 0 and 1). The toe tip rides the blended toe rigidly. (3) The solve is split into three computes by output: the controls' offsets (reading the ik and ankle plugs and the controls), the ankle socket (never the ankle plug) and the toe with its sockets. The foot control's own offset now depends on the ankle plug only through the toe FK control sharing its `controlOPM` array, so a channel dirties it when the Limb's end moves. (4) `ikFkDriver` is a connection: `ModuleInterface` gained `blendSource` (the attribute a module offers, set by `TwoBoneIkSolve::makeInterface`, so TwoBoneIk and Limb both) and `blendDriver` (set by the follower), both empty by default, so no other module and no existing golden changes. `validateBlendDrivers` checks the driver is in the template, offers a blend, and is the module every child plug of the foot hangs from. Build pass 2 (`connectBlendDrivers`) connects the driver module's `ikFkBlend` attribute to the foot's: the same value as the settings control's channel, which feeds both, with no new path through the control. The foot's input is not keyable and not in the channel box, and cannot be set while connected (it is not locked: Maya refuses a connection to a locked attribute). (5) A visibility output hides the toe FK control at blend 1 and the foot control at blend 0, where no channel moves anything. (6) **Pivot socket names:** the roles `toe` and `toeTip` would collide with the bind joints' sockets `toe` and `toeTip` (the design page names both), so their pivot sockets are `toePivot` and `toeTipPivot`; the other roles keep their names. Sockets other than `ankle` start at index 1 of `outputSocketMatrix`, because `getSocketMatrixPlug` sends index 0 to the ankle array.

### D75. twistRamp: a template-set share of the fk roll that each Ribbon and Limb ik control takes
**Status:** Decided (signed off by the author 2026-11-25) and built the same day on branch `fk-hierarchy`. Amends D59 (`fkStyle`) and D62 (Limb). Motivated by the solomon neck: `neckFK_00`'s twist reached `neckTwistIK_00` in full, and a `Swing` constraint on the `start` plug could not shed it, because the roll comes from the fk control's own rotation (`fkRollAt` in `core/RibbonMath`) and not from the plug's parent.

A `twistRamp` moduleArgs key on `Ribbon` (needs `fkStyle`) and `Limb`: `[position, share]` pairs, positions strictly increasing in 0 to 1 along the ribbon, shares 0 to 1. An ik control takes `share` of the fk (a Limb's anchors') roll at its own parameter, linear between the pairs and held at the first and last share outside them. Default, no key or `[]`: every share is 1, which is the old 1:1 behaviour, so no existing rig changes.

- **What the share multiplies:** the whole roll at the control's place, in both uses of it: the ik control's frame (`evaluateControlsInternal`) and the twist the bind joints ease through (the detail curve), so the skin never disagrees with a control. Rejected: the share on only the start fk control's own roll (the shoulder-style ease), which needs the fk chain's rolls split into per-control contributions and says nothing about a roll on a later fk control. The ramp is the simpler rule, and `[[0, 0], [1, 1]]` gives the shed-and-ease result the neck needed.
- **Evaluated at build, stored per ik control:** `applyTwistRamp` turns the pairs into one share per ik control in the plan step, and `RibbonSolve` stores them in a `fkRollShare` double array (default 1, so a scene file keeps only what a ramp changed). `compute()` reads a share and multiplies, with no ramp parsing or interpolation per evaluation. Rejected: storing the pairs and evaluating per frame.
- **Not a channel (author):** it is rig data, in no pose or animation, and changing it means rebuilding. Shares are not signed, so mirroring copies them.
- **Ranges:** 0 to 1 only. A share over 1 would exaggerate a twist, nobody asked for it, and it is a one-line relaxation in `validateTwistRamp` if someone does. A position outside 0 to 1, positions that do not increase, `twistRamp` on a Ribbon with no `fkStyle`: build errors naming `moduleArgs.twistRamp`.
- **moduleVersion not bumped:** a new optional key that defaults to the old behaviour changes no old template's meaning. Public names: `twistRamp` (moduleArgs key) and the node attribute `fkRollShare`.
- **Inverse:** `ModuleInverseContext::fkRollShare` carries the stored shares, and the Ribbon's and the Limb's inverse apply them (`RibbonSolve::applyStoredShares`) so a restore runs the forward solve the ramp made. A fk-style Ribbon's restore leaves its fk controls at rest, where the roll is 0 and the share changes nothing.
- **Limb:** the Limb runs the ribbon solve with the blended joints as anchors, so the ramp there shares the roll of the root, mid and end joints. Positions are in the anchors' chord-share space (the mid joint at its share of the limb's length), which is the space of the stored `knotU`.
- **Consequence:** one shared attribute and a context field, two moduleArgs keys, three `core/RibbonMath` functions (`validateTwistRamp`, `applyTwistRamp`, a `Setup::fkRollShare` array), no new channel, no change to saved poses or animation. Evaluation cost: one multiply per ik control for an fk ribbon; not benchmarked (no new module or constraint type).

### D78. Every control and bind joint a module solves is a socket
**Status:** Decided (rule stated by the author 2026-11-26). The Ribbon step is built (2026-11-26), with questions 1 and 2 answered by the author as recommended: a bind socket has no DAG transform (matrix only), and the fk controls get `fk_<n>` sockets. The audit of the other modules (question 4) found two more gaps, built the same day: the Limb's ribbon ik controls (`ribbon_<n>`, with the control's transform; not `index_<n>`, which are the limb's three joints) and ReverseFoot's foot control and toe FK control (`foot` and `toeFk`, matrix only, at socket elements 8 and 9 after the five pivots). Layout, FkChain, FkHierarchy, Aim and TwoBoneIk were already complete. Still unbuilt: the contract check that every control in `ModuleInterface::controls` has a socket. Open: an FK control and its joint share one socket in TwoBoneIk and the Limb, so at ikFkBlend 1 the FK control's own world is not exposed. Amends D4 and D56; builds on D62 (the Limb's `bind_<n>`), D71 (markup-named sockets) and D77 (collision on a child plug).
**Built:** `makeRibbonInterface` and `createModule` in `RibbonModule.cpp`, `PlugAndSocketNames::Fk`, the goldens `ribbon_basic` and `ribbon_fk`, and `RibbonBindSockets` in `test_ribbon` (a child plug on `bind_2` and on `fk_1`, a constraint driven by `bind_2`). `compute()` and the inverse needed no change: `writeOutputMatrix` writes any socket element that exists, and the inverse already filled `socketWorld` for every slot.

**Problem.** A constraint driver and a child plug's parent are both a `module.socket` id (D4, D19). A thing with no socket cannot drive a `rigConstraint`, cannot feed a collision (D77) and cannot be a parent. The Ribbon builds one tweaker per bind joint and solves its world matrix every evaluation, then drops it (`writeSolvedSlot(..., hasSocket)` skips the slot). Twist joints are where the author wants to hang modules (a sleeve, a bracer, a collision probe) and nothing can attach to them. The Limb's own ribbon already exposes `bind_<n>`, so the same ribbon is attachable or not depending on the module.

**The rule (author, 2026-11-26).** Every module's controls are addressable as constraint targets, like in any rig, whether or not the thing is valid as a DAG child. Every joint a module solves is too. A socket is the addressing mechanism, so the rule is: a module declares a socket for every control and every solved joint it owns, and a socket is a matrix output, not a DAG commitment. The DAG half (the callback that reparents a child plug's control under the socket's transform) stays optional per module. A socket whose transform cannot be a parent still serves as a constraint driver, because the constraint reads the matrix plug, not the DAG.

**Naming, by module shape.**
- **Positional modules** (FkChain, Layout, Aim, TwoBoneIk, Ribbon, Limb, ReverseFoot): an index or a role. FkChain keeps `index_<n>`, `start` and `end`. Joints that are not controls take `bind_<n>` in bind joint order, as the Limb does (`PlugAndSocketNames::Bind`). No new names for a module that already names everything.
- **FkHierarchy** (a tree, D71): sockets are already named from joint markup, the side lowercased then the usage (`left_child_00`), so `fkHierarchy_00_M_MOD.left_child_00` already resolves, and that is the address the author asks for. The rule is that the first `_` separates the lowercased side from the usage, which the usage may itself contain. Nothing changes for it, but the audit below must confirm every control gets one, including a joint under a terminator.

**First step: Ribbon `bind_<n>`.**
- `makeRibbonInterface` adds `bind_0` to `bind_<n-1>` after the ik control sockets. A Ribbon's socket list grows and nothing is renamed or reordered, so saved poses, animation and exports are unaffected. The golden snapshot and the contract's interface check change.
- `createModule` registers a `RigModuleSocketInfo` for each bind slot: the tweaker as `oTransform`, the joint's rest world as `mRestWorld`, `outputIndex` the slot, as for the ik controls. `compute()` passes `hasSocket = true` for the bind slots. The value is `solve.mWorld[slot]`, already computed, so there is no new solve work.
- Slot layout is ik controls, then bind (tweakers), then fk controls. The socket output array is indexed by slot, so a bind socket's `outputIndex` is `controlCount + i`. The Limb's own offset (`LimbSlot::FirstRibbon`) is the model to follow.
- `RibbonModule::inverse` fills `socketWorld` for the bind slots, so a restore leaves the sockets consistent with the joints.
- Constraints and collisions need no code change: both resolve through `findSocketById` and the socket matrix plug.

**Open questions (need the author).**
1. **Child plug on a bind socket: the DAG parent.** `reparentChildPlugToSocket` reparents under the socket's `oTransform`. For a bind socket that is the hidden tweaker. Options: (a) accept it (a child's controls sit under a hidden tweaker in the outliner; nothing transforms by the DAG, D1); (b) reparent under the bind joint instead; (c) leave the child where it is and connect the matrix only, as D55 does for another rig's sockets (`reparentDag = false`). Recommended: (c) for bind sockets, so the visible hierarchy does not change and no control sits under a hidden node. To confirm in code before building: how the callback treats a socket with no control (the Limb's `bind_<n>` is the existing case).
2. **The fk controls of a `fkStyle` ribbon** have no socket today ("an fk control has no socket and no joint"). Under the rule they get one too. Name: `fk_<n>`? Proposed: add them in the same change, since they are controls, and name them by index. Say if the fk controls should stay out.
3. **Tweakers as targets:** the tweaker and the bind joint have one world matrix, so one socket (`bind_<n>`) covers both. Confirmed by the Limb's comment ("the tweaker's world, which is the joint's").
4. **Audit scope.** Which other modules hold a control or solved joint with no socket? Known gaps from reading: the Ribbon's bind joints and fk controls (this change). To check: TwoBoneIk's pole and settings controls, Aim's parts (it exposes all `kAimPartNames`), Layout, ReverseFoot's toe FK control. The audit reads each module's `makeInterface` and its plan against its created controls, and a contract check can then enforce the rule: every control in `ModuleInterface::controls` has a socket whose matrix is its world. Proposal: build the Ribbon step now, run the audit after, and add the contract check with it.

**Rejected (author, 2026-11-26): a DAG fallback for matrix-only parents.** Found on the Solomon template: the fingers (`thumb_00_L_MOD`, `index_00_L_MOD`, `mid_00_L_MOD`) name `arm_00_L_MOD.end` in `parentStructure`, whose socket is matrix-only, so `reparentChildPlugToSocket` skips the DAG reparent and they sit loose in the outliner. The proposal was to keep accepting any socket and fall back to the nearest DAG-capable ancestor (the parent module's group or an upstream control), with a build warning. Rejected because it hides the difference between the two kinds of parent. The author wants `parentStructure` to say which it is. Direction (not built, needs a design and sign-off before code): `parentStructure` takes a DAG parent, and a matrix-only socket there FAILS the build with an error that says a valid `dagParent` must be given. Matrix-only sockets stay valid as constraint drivers. A `dagParent` is for parenting only (the fingers become the DAG child of the FK hand). The matrix a child follows is a separate key, a `matrixParent`. For the fingers the rigger gives the arm module's FK control as `dagParent` and `arm_00_L_MOD.end` as `matrixParent`. Which pair is correct is the rigger's responsibility (author, 2026-11-26): the build does not check that the two agree, so a rigger who names the FK hand as the matrix parent gets a rig that is wrong at IK, and that is theirs to fix. Still open for the design: whether `matrixParent` may be omitted (and then follow the `dagParent`) or is always required. This amends the "DAG half stays optional" rule above and the recommended option (c) of open question 1.

**Design: `dagParent` and `matrixParent` (author, 2026-11-26; proposed, not built, awaiting sign-off).**
- **Two parents per child plug.** The `dagParent` is the control the child plug's control is reparented under. It places the control in the outliner and decides what visibility it inherits, and nothing else (D1). The `matrixParent` is the socket whose world matrix feeds the child plug, so it is what the control follows and what a constraint reads as its parent (D31). `matrixParent` may be left out, and then it is the `dagParent`.
- **Strict.** A `dagParent` must be a socket that has a control transform. A matrix-only socket there fails the read phase, with the error naming the socket and saying a valid `dagParent` (a socket with a control) must be given. No fallback. Whether the pair is sensible is the rigger's job, the build does not check it. A matrix-only socket stays valid as a `matrixParent`, a constraint driver and (D77/D79) a collision reference.
- **Every control is a DAG socket.** Built 2026-11-26 in a simpler form than first written, with no new `fk_<n>` sockets on the Limb and TwoBoneIk: their FK control shares its joint's socket, as D78 already noted, and the socket now carries the control's transform, so `start`, `end` and `index_<n>` are DAG-capable (the matrix is still the blended joint's world, which is what a child wants). The Ribbon's and the Limb's `bind_<n>` carry the tweaker's transform. The ReverseFoot's `foot` and `toeFk` carry their controls' transforms. The sockets that stay matrix-only are the ones with no control: an Aim's `aim`, and the ReverseFoot's `ankle`, `toe`, `toeTip` and pivots. D78's open point about the FK control's own world at ikFkBlend 1 stays open: no socket gives it.
- **Template shape (recommended).** `parentStructure` keeps its name and its string values and means the `dagParent`, so a template that already names a socket with a control is unchanged. A new sibling key, `matrixParentStructure`, maps child plug to socket and is optional per plug. Alternative: one `parentStructure` entry that is either a string (dagParent, matrix follows) or `{ "dagParent": ..., "matrixParent": ... }`. The sibling key is additive and keeps one value type. For the Solomon fingers: `"parentStructure": { "start": "arm_00_L_MOD.fk_2" }` and `"matrixParentStructure": { "start": "arm_00_L_MOD.end" }`.
- **Core.** `ModuleInterface` gains the list of matrix-only socket names (next to `sockets`), so `RigTemplateValidation::validateParentStructure` can fail before anything is built. The contract checks it against the built sockets the way `RigModule.cpp` checks `hasControl` against `oTransform`. Mirroring swaps sides in both keys through `mirrorIdentifier`.
- **Build.** `RigBuild` pass 2 resolves the two sockets separately. `RigModuleDagReparentArgs` carries a dag socket and a matrix socket, and `reparentChildPlugToSocket` reparents under the first and connects the matrix of the second. The Limb and ReverseFoot callbacks follow. A `parent:` id (D55) is always accepted, as either parent: another rig's controls never become a DAG parent, so those entries stay matrix-only (`reparentDag = false`), as now.
- **Cycles.** The module graph takes its edges from the matrix parent, since a DAG parent adds no dependency (D1). A second check over the dag edges catches a DAG cycle, which Maya would refuse at the reparent anyway.
- **Built 2026-11-26.** `parentStructure` (the DAG parent) and `matrixParentStructure` in `core/` (`RigModuleData::matrixParentOf`, `ModuleInterface::matrixOnlySockets`, `validateParentStructure`, `validateMatrixParentStructure`, `resolveParentSocket`, a DAG cycle check beside the matrix one), `RigBuild::parentModuleControls` resolving two sockets (`RigModuleDagReparentArgs::dagSocket`), `RigControlNode::shown` (read by the draw override, bumped from `setDependentsDirty` and `postEvaluation`), `DagUtils::queueLockAndHideVisibility`, and the fixtures `parent_dag_parent_is_matrix_only`, `parent_matrix_parent_may_be_matrix_only`, `matrix_parent_unknown_child_plug`, `matrix_parent_unknown_socket` and `parent_dag_cycle` with two `TwoBoneIkBehaviour` cases. A plug with no control takes any socket in `parentStructure` (it has nothing to reparent), and a `matrixParentStructure` entry alone is enough for it. Not done: that a `shown` plug driven by the blend redraws in a GUI viewport, and that a hidden control is out of `boundingBox()` (frame all still includes it). The goldens `limb_arm`, `reverse_foot` and `twoboneik_basic` lost `visibility` from the driven controls' keyable list. It was never a channel there (a driven attribute is not one), so poses and animation are unaffected.
- **Hazard (resolved by `shown`).** Visibility inherits through the DAG regardless of `inheritsTransform`. The Limb hides its FK controls at IK and its IK controls at FK, so fingers under `fk_2` vanish at IK and fingers under `ik` vanish at FK. Nothing is visible in both, except controls that are not blend-dependent. The strict rule makes the rigger choose, and for a hand there is no good choice today. Decided (author, 2026-11-26): the choice of `dagParent` is the rigger's (a clavicle control with `end` as the `matrixParent` is valid, if unusual). The author wants the cause removed: switch the ik/fk display without the transform's `visibility`, so any control can be a `dagParent`. Options, none built: (A, preferred) a display attribute on `rigControlNode`, which draws itself through a VP2 draw override and has no shape node to hide, read by the override and driven by `aFkVisible` and `aIkVisible` instead of `visibility`, with `visibility` left to animators and tools; (B) a display-layer `overrideVisibility`, rejected for now because each control's layer already owns its `drawOverride` (one source per node, `DisplayLayerScene`); (C) a per-socket `blendHidden` flag that makes the validator refuse a blend-hidden control as `dagParent`, the fallback if A fails its probe; (D) the bind joint as the DAG transform of a blended socket, which has the same problem whenever the skeleton is hidden. A chosen (author, 2026-11-26), with no separate probe: the checks below are tests of the build, and C is the fallback only if they fail. They are whether the override redraws when the attribute is driven by an evaluated connection (`setDependentsDirty` does not run under parallel evaluation, see the note in `RigControlNode.h`), that a hidden control is neither pickable nor counted in `boundingBox()`, and what else reads a control's `visibility` (tests, tools).
- **Impact.** The template format changes: every template whose `parentStructure` names a matrix-only socket must be edited, and the build fails with the message above until it is. In this repo that is the Solomon template and, to find, the fixtures (`limb_bind_child`, `ribbon_bind_child`, `limb_foot`, `reverse_foot*`, `twoboneik_hand`, the `limb_*` that hang from `end`), `RigTemplates/Human.json` and `LayoutRig.json`. mayadev has parentStructure in 7 test files (`test_maya_asset_tools`, `test_maya_rigpanel` and others) to search before building. Saved poses, animation and exports are unaffected: no control, channel or existing socket is renamed, `fk_<n>` is added. Docs: `docs/templates.md`, `docs/modules.md`, `docs/attachments.md`, `docs/architecture.md`.
- **Tests when built.** A validation fixture for a matrix-only `dagParent` (the error text), one for an omitted `matrixParent`, a build test with a dag/matrix pair (the fingers' DAG parent is the FK control while their world follows the blended hand at IK), the `fk_<n>` sockets in the Limb and TwoBoneIk contracts and goldens, the DAG cycle check, a mirrored pair, and a `parent:` id.

**What it adds to the maintenance surface.** One more socket family on the Ribbon (`bind_<n>`, and `fk_<n>` if chosen), a rule in D4 that each control and solved joint has a socket, and a contract check for it. No new module, node, attribute or constraint type, so no perf rig change and no `bench` run (D36). Evaluation cost: output elements only. Constraints that read a bind socket depend on the whole ribbon solve, as any socket from it does.

**Impact.** Additive: saved poses, animation, shape files and exports are unaffected. Public names added: `bind_<n>` on the Ribbon. mayadev: nothing breaks, since only names are added.

**Tests when built.** The Ribbon contract and golden, a `test_ribbon` case that drives a `rigConstraint` from `bind_<n>` and checks its world against the bind joint's under a posed ribbon, a template with a child plug on a bind socket (including a mirrored one, which swaps `left_` and `right_` only on markup names, D71, so `bind_<n>` needs no swap), the inverse round trip, and the contract check for the rule.

### D79. Push out: one control out of one capsule
**Status:** Decided and built 2026-11-26 on branch `pushout` (the author approved `design/push-out.md` and asked for it to be built). Not done: perf rig instances and the one `bench` run (author, 2026-11-26: after the build is verified). Replaces D77. D77's work (a rig-wide collider file, probes, a solved swing and push, authoring tools) is parked on the `collision` branch, tag `collision-archive` in both repos, and will not be merged.

The author tested D77 on the solomon spine pouches and found it grew into a small physics system that is complex to set up, when the need was a collar pushed out of a head. Real collision belongs in the engine's physics. This keeps one thing.

- **A `collisions` list (author, 2026-11-26):** a new flat top-level template list, each entry with a `type`, and `PushOut` the only one. Not the `constraints` list, because collisions come after constraints: the build makes constraints first, and a collision runs after the constraint on its target. No `drivers`. It has a `capsule` (`follow` joint selector, `radius`, `halfLength`, an `offset` of translate and rotate with no scale), `margin`, `maxPush` and `constraintWeight`. One per target, run after the target's space constraint.
- **Solve:** the target control's origin at the plug's current frame, against one capsule, closed form and stateless. A push along the line from the capsule axis, translation only, capped by `maxPush`, scaled by the weight. On the axis the push is along the capsule's local +Z.
- **Rejected:** the collider file, probes and shapes other than the capsule (a collision system, not a constraint); a swing and a cone (the author wanted a predictable push); an authoring command set (a temporary display and a command that reports the `capsule` text replace it).
- **Display (author):** `showRigPushOuts`, `getRigPushOutCapsule` and `hideRigPushOuts`. The display is not part of the rig; the template holds the numbers. `getRigPushOutCapsule` only returns the text. Writing it into the template file waits for a larger rig template authoring tool (author, 2026-11-26).
- **Limits:** one capsule, one point, no memory between frames, no rotation. A hinge limit would be its own `type` and its own design.
- **New node:** `rigPushOut`, MTypeId `0x002196`, so it never clashes with the archived `rigCollision` (`0x002195`).
- **Consequence:** a new kind of constraint node, so it needs perf rig instances and one `bench` run when built. No new file format, no mayadev change.
