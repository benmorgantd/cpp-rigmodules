# Decisions: Skin weights

Smoothing, the skin weight brush and the rest-match brushes. Part of the decision log: the Index and the open items are in [`../decisions.md`](../decisions.md). Entries are in number order.

### D64. `smoothSkinWeights`: neighbor-average smoothing on a working set, built to be a brush later

**Status:** Decided (author, 2026-11-19: the vertex counts in its own average, `strength`, locked influences respected, a one-time brush-rate check). Built.

A rigger smooths skin weights by averaging each vertex with its neighbors, two or three times. It must be fast enough to become a brush context (15 fps or better on a dense mesh) and undoable.

- **Command:** `cmds.smoothSkinWeights(*objects, iterations=3, strength=1.0)` returns the vertices changed. Objects are meshes or vertex, edge and face components (edges and faces count as the vertices they touch). With none named it reads the selection, the third command to do so after `setRigMeshId` and `pruneToMaxInfluences` (D14, D35). Undo restores the starting weights exactly.
- **Algorithm:** each pass sets a vertex to the average of itself and its neighbors, blended by `strength`, reading only the previous pass (Jacobi), so every vertex updates at the same time and vertex order changes nothing. The vertex is in its own average (author): on a quad mesh, which is bipartite, a plain neighbor average swaps a checkerboard pattern every pass and never damps it.
- **Why it is fast:** the neighbors of only the vertices being smoothed are asked of the mesh (`MItMeshVertex`), so a selected ring costs the same on a small and a dense mesh (author: it is smoothed from a hotkey). A whole-mesh smooth builds the map in bulk from the polygon loops (`MeshAdjacency`). Nothing about topology is kept between calls, so there is nothing to go stale on a mesh edit; the first design cached the map per mesh and was rejected for that risk. Only the working set (the target vertices and their neighbors) is read, so a dab costs what its vertices cost and not what the mesh costs. Only the unlocked influences with weight there are carried: a patch of skin has a handful of the cluster's dozens. Only the vertices that moved by more than 1e-9 are written, over only those influences, in one `setWeights` call.
- **Locked influences (author):** a joint's `lockInfluenceWeights` is read once at bind. A locked influence keeps its weight on every vertex, and the unlocked ones keep the total they had, so the row still adds up. The cluster's `maintainMaxInfluences` is kept: a smoothed vertex keeps its largest `maxInfluences` weights, locked ones counting towards the limit and the unlocked ones keeping at least one.
- **Layers:** `core/SkinWeightSmooth` has no Maya and takes the weights through a fetch callback. `SkinWeightSmooth` in `SkinWeightScene` binds a mesh once (skinCluster, locks, max influences) and then `prepare`s, applies and undoes any number of times, which is what a brush reuses. `MeshUtils::getVertexTargets` turns a selection list into meshes and vertex ids: meshes, faces, edges and vertices all work (author).
- **Threading was looked at and not done (author asked, 2026-11-19).** On the 50k mesh the whole-mesh command is about 260 ms, of which Maya's `getWeights` (about 75 ms) and `setWeights` (about 135 ms) are most, and neither is thread-safe. Each extra pass costs about 10 ms, so threading the passes saves at most about 30 ms.
- **Measured (author asked, 2026-11-19; scratch scripts, not part of the suite):** a 223 x 223 plane (50 176 vertices, 40 influences, 4 per vertex). The whole mesh at 3 passes is about 250 ms, mostly Maya's `getWeights` (about 75 ms) and `setWeights` (about 135 ms). A one-vertex or dab call is about 19 ms, and our own work in it (bind, neighbors, the smoothing) is about 0.4 ms. The rest is Maya re-evaluating the skinned mesh after the last weight edit, about 9 ms the first time anything touches the mesh (a `MSelectionList::add` of a component after any `setWeights` pays it, and so does `cmds.skinPercent` on one vertex) and about 10 ms in the write. The viewport pays the same evaluation after any edit, so a brush's rate is set by Maya's skin evaluation and not by this code. The first design cached a neighbor map to save what turned out to be about 1 ms. Not measured: a real brush context.
- **Brush:** built in D65.
- **Names and format:** additive: a new command and no changes to a saved file or name. mayadev gets a menu entry in the weights submenu.

### D65. The skin weight brush: one context for every skin painting command, falloff over the mesh surface

**Status:** Decided (author, 2026-11-19: surface falloff from a radius that is a length over the mesh, a through-the-mesh pick, one context for future skin brushes, a fast visualizer, the closest hit across meshes with a stroke that can cross meshes, Ctrl + drag to resize, no hold-to-repeat). Built. The GUI side is not verified.

A rigger paints skin weights by dragging a brush over a skinned mesh. The first brush smooths (D64). More will follow (add, scale, replace), so the context is not about smoothing.

- **Layers:** `core/SurfaceBrush` (no Maya): `SurfaceDistance`, `brushFalloff`, `StrokeJournal`. `shared/SkinBrushStroke`: `SkinBrushOperation` (what a dab does), `SkinBrushStroke` (picking, reach, dabs, journal) and `SkinBrushEdit` (a finished stroke). `contexts/SkinBrushContext`: `skinBrushCtx`, the `MPxContext`, and `skinBrushStroke`, the `MPxToolCommand` that is the undo step. The context only handles events and drawing. A new brush is a `SkinBrushOperation` and a line in `createBrushOperation`: the picking, falloff, visualizer, undo and both commands come with it.
- **Falloff is over the surface (author).** The radius is a length measured along the mesh edges (Dijkstra) from the corners of the face the ray hit, so a brush never reaches across a gap or through a thin wall to a part of the mesh it is not connected to, and two shells never share a dab. The first design was a ball in space with a connectivity filter and a spatial grid; the surface distance does both jobs and the grid is gone. The distance is over edges, so it is a little longer than the true surface distance on a diagonal.
- **Picking.** The ray is cast against the deformed mesh with `MFnMesh::closestIntersection`, over every selected skinned mesh, so the closest surface wins and a stroke can move from one mesh to another (author). With `throughMesh`, `allIntersections` hits every surface the ray crosses and each is dabbed once (author: painting the back of a mesh). The accelerator and vertex positions are built when the tool starts, and positions are read again at each press and when the pointer re-enters the viewport. A mesh that deforms during a stroke (the weights change the skin) is not re-read within the stroke.
- **One undo step per stroke.** Dabs write as they go so the user sees them. The journal keeps the first weight of each vertex and influence a dab changed (first write wins, so overlapping dabs undo to the true start). At release the stroke reads the final rows of the touched vertices, and the tool command keeps whole rows from before and after, so undo and redo each write one `setWeights` per mesh. A stroke is journaled as the same command with each dab as a `hitPoint` (a through-mesh dab with several hits becomes several dabs when replayed).
- **Falloff mode (author, 2026-11-19): `surface` or `volume`.** `volume` is the plain distance in space from the hit point, found with one pass over the vertex positions (no grid: about 0.1 ms for 50k vertices), for reaching a part of the mesh that is close but not connected. It is a setting, not a connectivity filter on the surface mode, so the two stay simple. Surface stays the default.
- **Default radius (author, 2026-11-19: the first radius, 5 units, was tiny on a character 100 times larger than the test plane).** Until the user sets one, the radius is 5% of the diagonal of the box around the selected meshes, read when the tool starts. A set radius (a flag, a resize) is kept.
- **Drawing and dabs, after a GUI test (author, 2026-11-19).** Drawing in the event handlers left rings behind, so the ring and the reach are drawn in `drawFeedback` only, as Maya's own brush sample does, and the handlers ask for a redraw. A drag dabs every quarter radius along the pointer's path, by screen distance, so a fast drag leaves no gaps. Any button but the middle one starts a stroke, in case a trackpad click does not report as the left button.
- **Drag and hold drawing, second pass (author, 2026-11-20, after comparing another design's notes).** Each dab costs a skin evaluation, so a drag event now spends at most 40 ms dabbing and then skips to the pointer instead of catching up (a gap on a fast drag, no lag behind the pointer). The ring and reach keep the last surface they were on when the pointer leaves the mesh mid-stroke. The viewport is refreshed at once after a drag or repeat dab that landed, so the new weights show under the pointer. Rejected from that design: a live weight buffer and a Qt timer (the stroke engine and `MTimerMessage` already do both), and a `B` key resize (Ctrl + drag stays). Not verified in a GUI Maya.
- **Strength per vertex** is `strength * falloff`, through `SkinSmoothSettings::vertexScale`, empty for the command, which is unchanged. A dab is one smoothing pass: a stroke supplies the repetition.
- **Rate.** No thread. One dab runs per processed drag event and only after the brush moved a quarter of its radius, so events pile up no faster than Maya can skin the mesh. **Hold to repeat (author, 2026-11-19, reversing "none in v1"):** a single dab at strength 0.5 was too gentle to paint with. While the button is down an `MTimerMessage` callback ticks every 0.05 s (20 a second; it was 0.1 s, doubled by the author on 2026-11-20 to paint faster) on the main thread and, when no dab landed since the last tick, dabs again at the last pointer position, ignoring the spacing rule. The first version also skipped a tick after any drag event, so the jitter of a held mouse or trackpad stopped the repeat (author's GUI test): only a dab that landed counts as movement now. `MPxContext::doHold` is deprecated since Maya 2024 in favor of exactly this. The timer starts at press and stops at release, tool change and context deletion. D64 measured about 20 ms of Maya skin evaluation per edit on 50k vertices, so the ceiling is near 40 fps against the 15 fps target. Not measured in a real session.
- **Settings:** `radius` (a length over the surface), `strength`, `operation`, `throughMesh`. Ctrl + left drag resizes. Holding the brush still repeats the dab. A selection of vertices or faces limits the brush to them, read when the tool starts and when the pointer re-enters the viewport.
- **Visualizer:** a ring at the hit, and one point per vertex the next dab reaches, coloured by falloff, drawn in one `MUIDrawManager::mesh` call with a depth priority that keeps it on top. The reach is computed once per pointer move, the same reach the dab uses, so the picture is what a dab does.
- **Tests:** `skinBrushStroke` replays a stroke from hit points or rays, which tests the falloff, the surface distance, the closest-surface and through-mesh picking, multi-mesh strokes and undo below the mouse. Maya creates no contexts in `mayapy`, so the `skinBrushCtx` settings test is skipped in the suite and runs in a GUI Maya. Not tested anywhere automatically: events, the drawing, Ctrl + drag, the selection restriction.
- **Names:** additive. Flag names are not `hit` or `ray`, because Maya drops a three-letter long flag name without an error (`hitPoint`, `viewRay`).
- **Maintenance surface added:** one core file, one engine file pair, one context file pair and a `maya/contexts/` folder, two commands, `vertexScale` on the smoothing settings.

### D66. Rest-match brushes: paint weights in a pose so the mesh goes back towards its rest deltas or edge lengths

**Status:** Decided (author, 2026-11-20: the skinCluster's input geometry is the rest shape, linear blend skinning only, two operations named `restDelta` and `restEdge`). Built. Brush feel in a GUI Maya is not verified.

The author wants a brush like a delta mush, painted: pose the rig, and paint weights so the mesh in that pose matches its rest deltas or rest edge lengths, instead of smoothing (D64, D65).

- **The model.** With linear blend skinning a vertex's posed position is `sum(w_k * c_k)`, where `c_k` is where it would sit if bound to influence `k` alone (rest point times `bindPreMatrix * joint matrix`). It is linear in the weights, so each vertex is a small least-squares problem over the simplex (weights at least 0, the row's unlocked total fixed), solved in `core/SkinWeightRestMatch` by projected gradient with a weak pull (1e-3 of the spread of the candidates) towards the starting weights, which only picks one answer when more than three influences fit equally.
- **Where the vertex should sit.** `restDelta`: the average of the neighbors' posed positions plus the rest delta (rest position minus the average of the neighbors' rest) turned by the polar rotation of the skin's blended matrix at the vertex, as a delta mush does. Edge angles are inside the delta, so there is no angle operation. `restEdge`: the average over the edges of the point at the rest length from the neighbor along the edge's current direction (a position-based-dynamics distance constraint). A dab's strength is `strength * falloff` of the move from the old weights to the solved ones, the same meaning as smoothing.
- **Same structure as smoothing.** One `SkinBrushOperation` class with a target, listed twice in `createBrushOperation`: no new flags, no new command, and the picking, falloff, visualizer, journal and undo come with it. Each vertex reads the neighbors' pose as the last pass left it (Jacobi). The pose of the working set is computed from the fetched weights and cached joint matrices, never by re-reading the deformed mesh, so a dab costs what a smooth dab costs and the neighbors are current within a stroke. Only influences with weight in the working set and not locked take part; `maxInfluences` uses the shared `keepLargestWeights`.
- **Rest source (author): the skinCluster's `input[0].inputGeometry`**, taken to world space with `geomMatrix`. Rejected for now: a `restMesh` flag for a sculpted target.
- **Linear blend only (author).** `bind` fails for `skinningMethod` other than 0, and it compares the model with `getPoints` on up to 2000 vertices (tolerance 1e-3 of the mesh's largest extent) and fails when they differ, so an unsupported setup (a deformer after the skinCluster, a bind that does not match the rest pose) is an error, not a silent wrong pose.
- **Refactor with the change.** The plumbing of `SkinWeightSmooth` (binding the skinCluster, locks, the weight fetch, apply, undo) moved into a base class `SkinWeightPass`, which `SkinWeightSmooth` and `SkinWeightRestMatch` derive from. `keepLargest` became the shared `keepLargestWeights`. `SkinBrushOperation` gained a `refresh()` (default does nothing) that `SkinBrushStroke::refresh` calls at each press so the joint matrices follow the pose.
- **Limits.** It blends the influences the neighborhood already has, so it cannot fix a candy wrapper that needs a new influence. Weights fitted to one pose can hurt another, so paint in several poses. One pass per dab, with neighbors fixed, converges over repeated dabs (hold to repeat).
- **Smoothness (author, 2026-11-20, after using the brushes: `restEdge` can crunch, `restDelta` smooths a lot but is predictable).** A `smoothness` setting, 0 to 1, default 0.15, on `skinBrushCtx` and `skinBrushStroke`, applied by both rest operations and ignored by `smooth`. After every vertex of a dab is solved, each change (solved weights minus starting weights) is blended with the average change of its neighbors (a neighbor the dab did not reach counts as no change), then projected back onto the simplex and scaled by strength and falloff. Rejected: pulling each vertex's weights towards its neighbors' weights, which would smooth a pose that already fits and so break "at rest nothing changes". Blending the changes keeps the fixed point. `SkinBrushOperation::prepare` and `SkinBrushStroke::dab` gained the parameter.
- **Names and format:** additive: two operation names and the `smoothness` flag. Saved weights are unchanged.
- **Maintenance surface added:** one core file pair, a base class and one class in `SkinWeightScene`, an operation class, `keepLargestWeights` shared.
