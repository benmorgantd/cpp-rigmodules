# Architecture

How the code is organized and how a rig comes to exist, for people reading or changing it. It describes what is built. The reasons behind each choice are in [`../design/decisions.md`](../design/decisions.md), cited here as `D<n>`. For what a user can do, see the other pages listed in [README.md](README.md).

## Layers

```
 Python (python/rigmodules)      thin wrappers over commands, for pipeline tools
        |  cmds.*
 Commands (cpp/maya/commands)    parse flags, delegate, report
        |
 Nodes and scene code            cpp/maya/modules   module nodes (Layout, FkChain, Aim)
 (cpp/maya)                      cpp/maya/nodes     rig root, asset root, constraint, control
                                 cpp/maya/shared    module base, scene helpers, traversal, utilities
        |  includes
 Core (cpp/core)                 no Maya headers: template structs, validation, markup,
                                 file formats, shapes, constants, string and JSON helpers
```

- **Dependencies point down only.** `core/` never includes Maya or `maya/` (D13). `tests/maya/concepts/test_source_layout.py` checks this, along with the include rules and brace style.
- **The plugin is one `.mll`** built from `cpp/RigModules.vcxproj`. `core/` is a folder, not yet a separate library.
- **Logic goes as low as it can.** If it needs no Maya header it goes in `core/`. The plugin layer is adapters between Maya and the core.

## Plugin startup

`initializePlugin` in `maya/PluginMain.cpp`:

1. Validates the control shape library. A shape that does not triangulate makes the load fail, because it would draw wrong in every rig.
2. Registers every `ModuleDescriptor` in `ModuleRegistry::all()` as a node, then `rigControlNode` as a transform with its draw override, then every `CommandDescriptor` in `CommandRegistry::all()`.
3. Starts `ActiveSelection`, the selection callback the draw override reads. It is last because Maya does not call `uninitializePlugin` after a failed load.

`uninitializePlugin` reverses this. Nothing in `PluginMain.cpp` changes when a module or command is added: the registries are the extension points.

`ModuleDescriptor` (in `maya/shared/RigModule.h`) is one table row per node:

| Field | Meaning |
|---|---|
| `nodeName`, `typeId`, `creator`, `initialize` | What `registerNode` needs |
| `moduleType` | The JSON `moduleType` string (`"FkChain"`) |
| `argUpdates` | Update steps for older `moduleArgs` (D33) |
| `plan` | `ModulePlanFn`: the read-phase step. `nullptr` means the node is registered but not buildable from JSON |
| `inverse` | The module's inverse (D41). `nullptr` for nodes that are not rig modules |
| `isRigModule` | Connects to a rig root's `rigModules`. Its `moduleType` is a valid `getRigControls` filter |

Node ids are listed in `CLAUDE.md`. Check that list before picking an id for a new node.

## A rig in the scene

```
assetRootModule
  .children --> rigRootModule            asset root, one per asset (D29)
                  .rigModules[] --> layoutModule, fkChainModule, aimModule ...
                  .constraints[] --> rigConstraint ...
                  .jointDisplayLayer, .meshDisplayLayer, .controlDisplayLayer  (D38)
                  .selectionSets[]                                              (D39)

module node
  .controlInputData[i]   .controlLocalMatrix  <-- control.matrix
                         .controlRestWorld    (stored at build)
  .childPlugs[k]         .childPlugParentMatrix, .childPlugParentRestMatrix  <-- a parent's socket
  .controlOPM[i]    --> control.offsetParentMatrix
  .jointOPM[i]      --> joint.offsetParentMatrix        (modules with joints)
  .outputSocketMatrix[s]  world matrix a child can attach to
  .socketNames[s]         the name of each socket
  .controlMessage[i] --> control.rigModule              how tools find a module's controls
```

Everything is found by connections, not names (D24, D25): `RigTraversal` goes rig root to modules to controls through the message plugs above.

The pieces:

- **Control** (`rigControlNode`, `maya/nodes/RigControlNode`): a transform with a `controlMarkup` attribute (side, usage), shape attributes, and a VP2 draw override. Shapes are meshes from the generated library. A module sets each control's rotate order, and the build locks it (D40). A control's animation interface is its keyable, writable channels (D34).
- **Joint**: a Maya joint carrying `rigMarkup` (side, usage, export, skin). A module drives it through `offsetParentMatrix`. `inheritsTransform` is off for controls and joints, so DAG parenting organizes the outliner and never drives a result (D1).
- **Socket and child plug**: a socket is a world-space matrix output a module publishes (`start`, `end`, `index_<n>`). A child plug is a module's input for attaching to a socket. The template's `parentStructure` maps child plug to socket (D4).
- **Constraint** (`rigConstraint`, `maya/nodes/Constraints`): one node type for Parent, Orient and Point (D31). It sits between a parent socket and a child plug and outputs the delta the child plug sees, switched by the control's `space` attribute. `computeDelta` is shared with the inverse solve.
- **Layout**: every rig has a `layout` module with three root controls. Child plugs a template does not parent attach to `layout.end`.

## Module nodes

Maya nodes cannot use ordinary inheritance with static `MObject` attributes, so the shared layer is a chain of CRTP templates in `maya/shared/RigModule.h`, each adding attributes and helpers on top of the one below:

```
MPxNode
  RigModuleNodeBase                    build, lookup and plan helpers (static). compute() base.
    RigModuleNode<T>                   moduleData, rigRoot, side
      RigModuleWithControlsNode<T>     controlInputData, childPlugs, controlOPM, controlMessage,
                                       outputSocketMatrix, socketNames, and the chain solve
        RigModuleWithJointsNode<T>     jointOPM, jointRestWorld, wireJoint
```

| Module | Base | Joints | Controls | Child plugs | Sockets |
|---|---|---|---|---|---|
| `LayoutModuleNode` | WithControls | none | 3 | none | `index_0`..`index_2`, `end` |
| `FkChainNode` | WithJoints | n | n | `start` | `index_<n>`, `start`, `end` |
| `AimModuleNode` | WithJoints | 1 | 2 (target, up) | `aim`, `target`, `up` | `aim`, `target`, `up` |

A module has the same four pieces. A new one copies FkChain:

1. **Node class**: `creator`, `initialize` (create, add and `attributeAffects` for every attribute), `compute`, and `static createModule(...)` that creates the node, its controls and joints, and returns a `RigModuleBuildResult`.
2. **Args struct** with `NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE`: the shape of `moduleArgs`.
3. **`planFromJson`**: the read-phase step (below). It reads the args, claims joints, declares the module's `ModuleInterface` and captures everything `createModule` needs in a lambda.
4. **`inverse`**: the module's controls from joint matrices ([The inverse solve](#the-inverse-solve)).

Then add one row to `ModuleRegistry.cpp`.

## Building a rig

`createRigFromTemplate` (`commands/CreateRigCmd`) resolves its flags into `RigBuildInputs` and calls `RigRootNode::createRig` (`nodes/RigRoot.cpp`). The build has two phases so that a bad template leaves nothing behind (D17, D5).

**Read phase** (`planRig`): reads the scene and never writes it.

1. `loadRigTemplate` runs the template's update steps, checks keys, then parses.
2. `TemplateMirror::expandMirrors` adds the other side's copy of every mirrored module and constraint, so every later step sees ordinary entries.
3. Header, module name and target-name checks. Every input joint's markup is collected into a `MarkedJointSet`.
4. `RigModuleNodeBase::planModules` runs each module's `plan` step. A plan resolves `[side, usage]` selectors to joints through `claimJoint`, reads rest matrices, and returns a `ModulePlan`: a name, a `ModuleInterface` (controls, child plugs, sockets) and a `build` closure.
5. `validateConnections` and `validateControlMarkup` check every `parentStructure` and constraint against the plans' interfaces. Joints marked for export that no module drives produce a warning.

Every problem goes into one `ValidationReport` with its JSON path, and `createRig` reports them all at once. Any error stops here.

**Write phase** (`buildRig`): runs only on a clean report, inside a `ScopedRigNamespace`, through one `MDagModifier` so undo and redo replay it.

1. Asset root (if none exists for the asset), rig root.
2. **Pass 1**: `buildModules` calls every plan's `build` closure, layout first, and checks each result against the plan's interface.
3. **Pass 2**: `parentModuleControls` connects every child plug to its `parentStructure` socket, or to `layout.end`. It reparents controls in the DAG for organization and connects the socket matrix to the child plug's `parentMatrix`.
4. Moves the input joints into the rig namespace, then the first `doIt`.
5. After it: display layers (`DisplayLayerScene`, D38), selection sets (`SelectionSetScene`, planned by `core/SelectionSets`, D39), rotate-order locks (D40), then the template's constraints (`RigConstraintNode::buildFromTemplate`). Constraints come late because they add an enum attribute to controls that must exist by then.

A failure after the first `doIt` calls `undoIt` before returning.

## Evaluation

All transform math is in the module nodes' `compute`. Aim solves its own three parts once per evaluation (`MathUtils::computeAimMatrix`: the aim joint's +X at the target control, +Z toward the up control, then the offset that keeps the joint's rest orientation). For a chain (`solveFkChain`, shared by Layout and FkChain):

```
parentDelta      = motion of the child plug's parent socket since rest   (MathUtils::computeDeltaFromRest)
controlOPM[i]    = controlRestWorld[i] * parentDelta
controlWorld[i]  = controlLocal[i] * controlOPM[i]                       (solveControlStep)
socket[i]        = controlWorld[i]
jointOPM[i]      = controlWorld[i]
parentDelta      = motion of control i since rest, for control i + 1
```

- The control's `matrix` goes in, and `offsetParentMatrix` comes out, so the control's own transform is purely its local channels. That is why animation lives on control channels only (D27, D34).
- Rests are stored at build time (`controlRestWorld`, `childPlugParentRestMatrix`, `jointRestWorld`) and never change. Skin weight loading binds new influences at `jointRestWorld` (D35).
- `compute` is kept free of allocations and string lookups. One solve per evaluation writes every output array and marks them clean. Performance goals and the measuring tools are in D36 and [`../tests/README.md`](../tests/README.md#performance-scenes).

## Commands

Every command is an `MPxCommand` with the same shape (D14):

- Long flag names are file-local `constexpr` constants. `newSyntax()` is the only place short names appear.
- A file-local helper reads the flags into a struct or value before anything is queued. `doIt` parses, delegates and returns.
- Nodes are passed by name as string objects, never taken from the selection. The two exceptions read the selection when no mesh is named: `setRigMeshId` and `pruneToMaxInfluences`.
- State changes go through a modifier or edit object the command keeps, so `undoIt` and `redoIt` replay them.
- Command logic that is about the scene lives in a `shared/*Scene` class or a node, and commands call it. A command file holds no scene logic of its own.

| File | Commands | Calls into |
|---|---|---|
| `CreateRigCmd` | `createRigFromTemplate` | `RigRootNode::createRig` |
| `ConstraintCmds` | `createRigConstraint`, `setRigConstraintSpace` | `RigConstraintNode` |
| `JointMarkupCmd` | `rigJointMarkup` | `JointMarkupScene` |
| `RigControlCmds` | `getRigControls`, `getRigControlInfo`, `getRigControlChannels`, `getRigMirrorControl`, `saveRigControlShapes`, `loadRigControlShapes`, `mirrorRigControlShapes` | `RigTraversal`, `RigPoseScene`, `ControlShapeScene` |
| `RigPoseCmds` | `zeroRigControls`, `mirrorRigPose`, `flipRigPose`, `saveRigPose`, `loadRigPose` | `RigPoseScene` |
| `RigKeyCmds` | `getRigKeys`, `setRigKeys`, `saveRigAnimation`, `loadRigAnimation` | `RigKeyScene` |
| `RigInverseCmds` | `poseRigFromJointPose`, `animateRigFromJointClip` | `RigInverse`, then `RigPoseScene` or `RigKeyScene` |
| `RigInfoCmd` | `getRigInfo` | `RigTraversal` |
| `SkinWeightCmds` | `setRigMeshId`, `saveRigSkinWeights`, `loadRigSkinWeights`, `pruneToMaxInfluences` | `SkinWeightScene` |

The command reference is [commands.md](commands.md).

## File formats and versions

Every saved format is JSON with a `formatVersion`, read and written in `core/` with no Maya involved:

| Format | Core files | Owning doc |
|---|---|---|
| Rig template | `RigJsonStructs` | [templates.md](templates.md) |
| Control shapes | `ControlShapeFile` | [controls.md](controls.md) |
| Skin weights | `SkinWeightFile` | [skinning.md](skinning.md) |
| ControlPose | `PoseFile` | [library.md](library.md) |
| ControlAnim, and the keys payload | `ControlAnimFile`, `RigKeys` | [library.md](library.md), [commands.md](commands.md#keys-format) |
| JointClip | `JointClipFile` | [python.md](python.md#file-format) |

The release version (`PluginInfo::Version`) and each format's version are separate. A format's version goes up only when its data changes shape or meaning, and it gets an `UpdateTable` entry that brings old files forward (`FormatUpdate::runUpdates`). Modules declare theirs in `ModuleDescriptor::argUpdates`. Names are public API: renaming a control, channel, child plug or socket breaks saved poses, animation and exports (D33).

## The inverse solve

The reverse of a rig's evaluation: from joint world matrices to control values (D41, [`../design/inverse-solve.md`](../design/inverse-solve.md)). It backs `poseRigFromJointPose` and `animateRigFromJointClip`.

- **A module owns its inverse.** `ModuleDescriptor::inverse` takes a `ModuleInverseContext` (stored rests) and a `ModuleInverseInput` (joint worlds, parent delta, fallback locals), all indexed by the module's slot. It returns control locals, the forward socket worlds so the modules below can be fed, and `solved` with a reason. FkChain and Layout share `ModuleInverse::solveChain`.
- **`RigInverse::solve` is the driver.** It reads the rig's rests once, orders modules parents first, and sweeps them in memory for each JointPose, using `RigConstraintNode::computeDelta` for space switches. A ControlPose sidecar fills what the joints cannot give. It reads no posed scene state and writes nothing.
- **The command applies the result**: values through `RigPoseScene`, keys through `RigKeyScene`.

## Python package

`python/rigmodules` is a thin layer over the commands (D24, D30). It imports no Qt, no `bmaya`, no pxr and no numpy, and reads no environment variables or asset paths, so it runs in bare mayapy with the plugin loaded. Pipeline code reaches rig internals only through it. A piece of Python belongs here only if it would have to change when a RigModules node, attribute, flag or template key changes. The module list and every function are in [python.md](python.md).

## Tests

`tests/run_tests.py` runs the suite in tiers, in one watched mayapy process. A tier runs only if every earlier gating tier passed, so the first failure shown is the root cause. `tests/maya/rigtest/` has the shared helpers, and `ModuleContract` is the set of checks every module must pass (interface, control channels, the inverse round trip). Expectations are written by hand in data files, never recorded from the rig. Layout, case-file formats and where a new test goes are in [`../tests/README.md`](../tests/README.md).

## Recipes

**A new module** (gated by D12: state the animator-facing problem and get the design signed off first)

1. `maya/modules/<Name>.h/.cpp`: node class, args struct, `createModule`, `planFromJson`, `inverse`.
2. A row in `ModuleRegistry.cpp`, and a new `MTypeId` that is not in the list in `CLAUDE.md`.
3. Add both files to `RigModules.vcxproj` and `.vcxproj.filters`.
4. Tests: a `ModuleContract` subclass, pose cases, a golden snapshot.
5. Add many instances to the performance rig (`tools/perf/perf_scenes.py`) and run `bench`.
6. Docs: [modules.md](modules.md), the README modules table, and a decision entry.

**A new command**

1. `maya/commands/<Name>Cmd.h/.cpp` in the D14 shape, with scene logic in a `shared/` class.
2. A row in `CommandRegistry.cpp`, and the project files.
3. A test file in `tests/maya/commands/`, assigned a tier in `TIERS`.
4. Docs: [commands.md](commands.md), and the README's command list.

**A new file format**

1. A `core/<Name>File.h/.cpp` with structs, `serialize` and `deserialize`, and an `UpdateTable` if it has versions.
2. The scene side in a `shared/*Scene` class, and a save and load command pair.
3. Docs: a section in its owning page (see the table above).

**A change to saved data**: raise the format's version and add an update step. Never change the meaning of an existing version.

## Conventions

The code rules are in `CLAUDE.md` and `design/decisions.md` (D14). The ones most likely to catch a newcomer:

- Allman braces, tabs, sorted include blocks. All three are checked by `test_source_layout.py`.
- Prefixes: `o` for `MObject`, `p` for `MPlug`, `fn` for function sets, `a` for module attributes.
- Pass a named lvalue to any Maya function taking a non-const `MObject&`.
- Attribute name strings live in `RigAttr`, never as literals.
- Check every `MStatus`. In `initialize()`, every attribute needs create, add and `attributeAffects`.
- Look in `maya/shared/Utilities.h`, `maya/shared/RigModule.h` and `core/` before writing a helper. A helper that is not about one feature's own concepts goes straight into the shared layer.
- Command examples are Python `maya.cmds`, never MEL, with long flag names.
